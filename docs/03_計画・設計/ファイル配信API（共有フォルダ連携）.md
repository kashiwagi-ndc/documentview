# 仕様メモ（工程③ 反復の計画づくり）— ファイル配信API（共有フォルダ連携）

> **【次フェーズに延期】** 今回のミッション（表示機能の画面・動作イメージ固め）ではモックデータ（プロトタイプ内蔵のサンプルPDF/画像）を使うため対象外。既存システム（共有フォルダ）連携を検討する段階になったら着手する参考資料として残す。

## 今回やること
- **機能名**：ファイル配信API（共有フォルダ連携）
- **今回の目標（スプリントゴール）への寄与**：ツリーで選ばれたPDF/画像の実体を、共有フォルダから安全にブラウザへ届ける

## 仕様（AIが迷わないように具体的に）
| 項目 | 内容 |
|---|---|
| 対象ファイル | `backend/src/main/java/jp/nihondata/documentview/controller/FileStreamController.java`、`.../service/FileStorageService.java` |
| 対象の関数・IF | `GET /api/files/{fileId}/content` → ファイルバイナリをストリームで返す（`Content-Type` はメタデータの `fileType` から決定、`Content-Disposition: inline`、Range リクエスト対応）。`FileStorageService.resolvePath(fileId)` が `fileId → 許可ディレクトリ配下の実パス` を解決する。実パスは常にバックエンド内部でのみ扱い、フロントエンドやURLに直接晒さない |
| 対象外（やらないこと） | ファイルのアップロード・更新・削除（読み取り専用）、ZIP等での一括ダウンロード、ウイルススキャン連携（別途情シスの既存対策に委ねる前提。要確認） |
| 動作確認手順（できたの基準） | ①正当な `fileId` でPDF/画像が正しい `Content-Type` で返る／②許可ディレクトリ外を指す不正な `fileId`（パストラバーサル試行）は403/404で拒否される／③大きめのPDFでRangeリクエストにより部分取得ができる／④存在しない `fileId` は404を返す |

## 不確実性（まだ確定していないこと）
| 種類 | 内容 | いつ・どう確かめる |
|---|---|---|
| 複雑性 | 共有フォルダへのアクセス方式（アプリサーバーにマウント済みのローカルパスとして読めるか、SMBプロトコルで都度接続が必要か）が未定 | 情シスに確認。プロトコル接続が必要な場合は `jcifs-ng` 等のライブラリ調査が追加で必要 |
| リスク（脅威） | `fileId` と実パスの対応づけを誤ると、許可外ファイルへアクセスされる（パストラバーサル） | 許可ディレクトリのホワイトリスト検証を必須の完成条件にする（下記DoD） |
| リスク（脅威） | 機微文書のため、ブラウザ・プロキシでのキャッシュ残留リスク | `Cache-Control: no-store` 等のヘッダ付与を完成条件に含める |

## 完成条件メモ（⑤テスト・⑥レビューの合格ライン）
- [ ] パストラバーサル試行（`../` を含む `fileId` 相当の入力）が確実に拒否される自動テストがある
- [ ] 許可ディレクトリ外のファイルには到達できないことをコードレビューで確認
- [ ] レスポンスに `Cache-Control: no-store` が付与されている
