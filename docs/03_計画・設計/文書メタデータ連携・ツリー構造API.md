# 仕様メモ（工程③ 反復の計画づくり）— 文書メタデータ連携・ツリー構造API

> **【次フェーズに延期】** 今回のミッション（表示機能の画面・動作イメージ固め）ではモックデータを使うため対象外。既存システム（基盤システム）連携を検討する段階になったら着手する参考資料として残す。

## 今回やること
- **機能名**：文書メタデータ連携・ツリー構造API
- **今回の目標（スプリントゴール）への寄与**：基盤システムが渡す文書情報（メタデータ＋ファイルパス）から、文書と添付文書の親子関係（ツリー）をバックエンドで組み立て、フロントエンドに提供する

## 仕様（AIが迷わないように具体的に）
| 項目 | 内容 |
|---|---|
| 対象ファイル | `backend/src/main/java/jp/nihondata/documentview/controller/DocumentTreeController.java`、`.../service/DocumentTreeService.java`、`.../service/MetadataRepository.java`、`.../dto/DocumentTreeNode.java`、`.../dto/DocumentMeta.java` |
| 対象の関数・IF | `GET /api/cases/{caseId}/tree` → `DocumentTreeNode[]` を返す。`DocumentTreeNode { id, name, type("document"|"attachment"), fileType("pdf"|"image"), fileId, children[] }`。`MetadataRepository.findTreeByCaseId(caseId)` が基盤システムのメタデータDB／インデックスファイルを読み取る |
| 対象外（やらないこと） | メタデータの書き込み・更新（読み取り専用）、基盤システムとの双方向同期、ツリー構造のキャッシュ最適化（Sprint 1では都度取得でよい） |
| 動作確認手順（できたの基準） | ①テスト用の案件IDで `GET /api/cases/{caseId}/tree` を呼ぶと、文書と添付文書が親子関係を保った状態でJSONで返る／②存在しない案件IDでは404を返す／③メタデータに定義された表示順が `children` の順序に反映されている |

## 不確実性（まだ確定していないこと）
| 種類 | 内容 | いつ・どう確かめる |
|---|---|---|
| 曖昧性 | メタデータDB／インデックスファイルの具体的なスキーマ（テーブル定義・カラム名・親子関係の表現方法）が未共有 | 着手前に情シス・基盤システム担当へ確認し、サンプルデータを入手する。**本機能のブロッカー** |
| 曖昧性 | 「案件ID」を本APIがどう受け取るか（基盤システムからの起動時にURLへ埋め込まれるか等）が未定 | 概要メモの不確実性と同じ。基盤システム連携方式の確認と合わせて解決 |
| 複雑性 | メタデータの取得元がDBかインデックスファイルかで実装（JDBC接続 or ファイルパース）が変わる | ヒアリング結果に応じて `MetadataRepository` の実装方式を確定してから着手 |
