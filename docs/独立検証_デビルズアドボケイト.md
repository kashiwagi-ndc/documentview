# 独立検証（デビルズアドボケイト）— 工程横断テクニック

> キット同梱の横断テクニック。**重要な判断を、本体とは別の文脈（別セッション）のサブエージェントに「肯定」ではなく「反証」させる**ことで、思い込み・楽観バイアス・見落としを減らす。⑥レビューで使う「第三者視点レビュー」を、①③⑧にも一般化したもの。

## なぜ使うか
- 作った本人（または書いたAI）と同じ文脈だと、**前提ごと「OK」にしてしまう**。
- AIは「指摘しろ」と言われると何か出すが、「**肯定して」と言うと何でも肯定する**。だから役割を「反証（refute）」に固定する。
- これは**一次スクリーニング**。最終判断は必ず人間が持つ（責任は移譲しない）。

## いつ使うか（工程別）
| 工程 | 反証させる対象 | 問いの例 |
|---|---|---|
| ①構想 | 価値仮説・適合性判断・リスクの洗い出し | 「この案件がアジャイル不適合な理由を挙げよ」「価値が出ない筋書きは？」 |
| ③計画 | 仕様の曖昧さ・見積りの楽観 | 「この仕様だけで別人が作ると、どこで解釈が割れる？」「この見積りが甘い根拠は？」 |
| ⑥レビュー | コード差分（正確性・脆弱性） | 「攻撃者ならどこを突く？」「この差分が壊す既存挙動は？」（→ `templates/06_レビュー結果.md`） |
| ⑧ふりかえり | 改善項目の実効性 | 「この改善が次サイクルで回らない理由は？」「標語で終わっていないか？」 |

## やり方（5ステップ）
1. **対象を1つに絞る**：反証したい主張・判断・成果物を1つ決める（差分・仕様・価値仮説など）。
2. **別の文脈で立てる**：別セッション／別サブエージェントに、**最小限の材料だけ**を渡す（本体の思い込みを持ち込ませない）。
3. **役割を"反証"に固定**：「これを支持するな。**穴・反例・崩れる前提を探せ。迷ったら反証側**に倒せ」と指示する。
4. **重要度タグで仕分け**：指摘を 🔴致命（直さないと進めない）／🟡要改善／🟢軽微 に分ける。
5. **人が採否を決める**：出た反証のうち、**正確性・要件・安全に関わるものだけ**採用する。過剰設計・「将来のため」の指摘は採らない。

## ミニ・反証シート（任意）
```
対象：{{差分／仕様／価値仮説 等}}
反証の問い：{{攻撃者視点・別解釈・崩れる前提}}
出てきた指摘：
- 🔴 {{致命：理由}}
- 🟡 {{要改善：理由}}
- 🟢 {{軽微：理由}}
人の判断：{{採用＝○○を修正／不採用＝要件外 等}}
```

## ガードレール
- **反証は素材、結論ではない**：採否と最終判断は人間。AIに「検証済み」と言わせて責任を移さない。
- **多数決にしたいときは独立に複数**：同じ問いを複数エージェントに別々に反証させ、過半数が🔴なら止める、という使い方もできる（重要判断のみ）。
- **機密3原則を守る**：反証用エージェントにも本番データ・シークレットを渡さない。
- **やりすぎない（just enough）**：全タスクに使わない。**手戻りが大きい／不可逆／本番影響大**の判断にだけ使う。
