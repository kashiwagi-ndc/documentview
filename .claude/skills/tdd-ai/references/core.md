# TDDコア — 哲学・ワークフロー・アンチパターン

## テストの哲学

**核心原則**: テストは実装の詳細ではなく、公開インターフェース越しの「振る舞い」を検証する。
コードは全面的に変わってもよい。テストは変わるべきではない。

- **良いテスト**: 公開APIを通じて実際のコードパスを実行する。「ユーザーが有効なカートでチェックアウトできる」はそのまま仕様になる。リファクタ後も壊れない。
- **悪いテスト**: 内部の協調オブジェクトをモック、プライベートメソッドをテスト。振る舞いが変わっていないのにリファクタするとテストが壊れる。

> AI駆動開発での注意: Claudeは「テストしやすさのため」に内部関数を公開・分割しがち。
> 「公開インターフェースだけをテストする」を指示に明示すること。

## テスト命名規則

テスト名は「仕様書」として読めるように書く。

```
❌ 実装を説明している（悪い）:
  test_function_returns_true
  test_checkout_process

✅ 振る舞いを説明している（良い）:
  test_user_can_checkout_with_valid_cart
  test_checkout_fails_when_cart_is_empty
```

**命名フォーマット（推奨）**:
```
test_[主語]_[動詞]_[条件]
例: test_user_cannot_login_with_wrong_password
例: test_order_total_includes_tax_when_region_is_japan
```

## アンチパターン：水平スライス（絶対にやらない）

```
❌ 水平スライス（AI駆動開発で特に起きやすい）:
  RED:   テスト1, テスト2, テスト3 をまとめて書く
  GREEN: 実装1, 実装2, 実装3 をまとめて書く

✅ 正しい垂直スライス（Tracer Bullet）:
  RED→GREEN: テスト1 → 実装1
  RED→GREEN: テスト2 → 実装2
  RED→GREEN: テスト3 → 実装3
```

水平スライスが生む問題:
- 想像上の振る舞いをテストする（実装前なので実態と乖離する）
- テストが変化に鈍感になる（振る舞いが壊れてもパスする）

**Claude Codeへの指示でやりがちなNG**:
```
❌ 「この機能のテストを5本書いて、それから実装して」
✅ 「最初の1本だけテストを書いて。パスしたら次のテストを書く」
```

## プランニングフェーズ（実装前の確認）

```
[ ] どの振る舞いをテストするか優先度を決めたか？
[ ] 公開インターフェースの形を確認したか？
[ ] テスト可能な設計になっているか確認したか？
[ ] 何をテストしないか（スコープ外）を決めたか？
```

**Claude Codeへの確認パターン**:
```
実装を始める前に教えてください：
1. この機能で最も重要な振る舞いは何ですか？
2. 公開インターフェース（関数名・引数・戻り値）はどうあるべきですか？
3. 最初にテストすべき「Tracer Bullet」となる1つの振る舞いは何ですか？
```

## Tracer Bullet の原則

**1テスト → 1実装 → 繰り返し**が基本単位。

> IPA ITSS+アジャイル開発ガイド（2024）では「スパイク・ソリューション（別名：曳光弾）」として公式スキル項目に定義されている。

```
Tracer Bullet の流れ:
  1. 最も重要な振る舞い1つだけをテストする（最初の1本）
  2. パスする最小実装を書く
  3. 「この実装から何が見えたか？」を踏まえて次のテストを書く
  4. 繰り返す
```

## ワークフロー

### STEP 0: 仕様確認（BDD形式）— 必須・省略禁止

**BDD仕様は開発者だけで書かない。プロダクトオーナー（PO）・ステークホルダーと合意してから STEP 1 に進む。**
（出典：IPA ITSS+アジャイル開発ガイド「受け入れ基準はPOやステークホルダーとの間でも合意しておく」）

```
Feature: [機能名]

  Scenario: [シナリオ名]
    Given: [前提条件・システムの状態]
    When:  [ユーザーの操作・イベント]
    Then:  [期待される結果・振る舞い]
    And:   [変わらないもの（不変条件）があれば明示する]
```

**合意チェック（STEP 1 に進む前）**:
```
[ ] POがこのシナリオを読んで「これが完成の条件」と言えるか？
[ ] 「Then」の内容がそのままデモで見せられる状態になっているか？
[ ] 非機能条件（性能・セキュリティ）が必要な場合は And に追加したか？
```

#### Then の書き方：「変わったもの」と「変わらないもの」を両方書く（形式手法の知見）

Thenには期待する変化だけでなく、**変わってはいけないもの（不変条件）**も書く。
これによって、副作用バグ（意図しないデータ変更・状態汚染）をテストで検出できる。

```
❌ 変化だけを書いている（不完全）:
  Then: 注文レコードが作成される

✅ 変化と不変条件を両方書く（完全）:
  Then: 注文レコードが作成される
  And:  既存の他ユーザーの注文は変更されない
  And:  在庫数が注文数分だけ減る
  And:  在庫数がマイナスにはならない
```

#### 非機能要件をBDDに含める（IPA非機能要求グレードの知見）

クリティカルな機能では、BDD仕様に非機能の受け入れ基準を追加する。
追加すべきかの判断基準：**「テストで自動検証できるか？」** → YES なら書く。

```
Feature: ログイン

  Scenario: 正しい認証情報でログインできる
    Given: ログイン画面が表示されている
    When:  正しいメールとパスワードで送信する
    Then:  ダッシュボードに遷移する                    ← 機能
    And:   レスポンスが2秒以内に返る                  ← 性能（自動検証可）
    And:   パスワードがHTTPリクエストに平文で含まれない ← セキュリティ（自動検証可）
```

**非機能を追加する優先度（高い順）**:
```
1. セキュリティ  — パスワード平文・XSS・SQLインジェクション（常に書く）
2. 性能         — SLAがある、またはユーザー体験に直結する箇所
3. 可用性       — エラー時のフォールバック動作
4. 操作性       — アクセシビリティ要件（role・aria-label）
```

### STEP 1: Red（失敗するテストを書く）

```
以下のBDD仕様を満たすテストを書いてください。
実装コードはまだ書かないでください。

[BDD仕様をここに貼る]

テストを実行してRedであることを確認してください。
```

> **設計の臭いセンサー**: テストが書きにくいと感じたら設計の問題。
> - 依存が多すぎる → インターフェースを分割
> - 副作用が隠れている → 純粋関数に切り出す
> - グローバル状態に依存 → 引数で渡す

### STEP 2: Green（最小実装）

```
先ほど書いたテストをパスする最小限の実装を書いてください。
きれいさより「動くこと」を優先してください。
テストを修正してはいけません。
```

### STEP 3: テストスイート全体確認

```
全テストスイートを実行して、既存テストがすべてパスすることを確認してください。
失敗があれば、テストを変えずに実装を修正してください。
```

### STEP 4: Refactor（改善）— Greenになってから必ず行う

**必須ルール: Redの間はリファクタ禁止。Greenになってから行う。**

```
テストが通る状態を保ちながら改善してください：
- 重複の除去
- 命名の改善
- 深いモジュール化（小さいインターフェース・豊かな実装）

リファクタの各ステップ後に必ずテストを実行してください。
```

参考: `tdd/refactoring.md`

## BDDを先に書く理由（定量的根拠）

IPA「ソフトウェア開発における定量的管理の主な手法」（2019）より：

> **定量的管理を実施したプロジェクトの成功率: 45.6%（未実施: 24.3%）**
> 信頼性確保には「上流工程での品質作り込み」が不可欠。
> テスト後半での品質担保だけでは限界がある。

BDDで仕様を先に書くことは「上流での品質作り込み」そのものである。
テストを後から書いた場合、設計の欠陥はテスト工程まで持ち越される。

### テストケース密度を異常検知に使う

**テストケース密度** = テスト件数 ÷ 機能規模（画面数・エンドポイント数など）

カバレッジとは別の視点で、テストの「量的な偏り」を検出できる：

```
⚠️ 密度が急に下がっている箇所 → テストが薄い・スキップされた可能性
⚠️ 密度が突出して高い箇所   → 複雑すぎる・リファクタ対象

目的: 目標値の達成ではなく、偏りの検知に使う。
      カバレッジ数値を目標にするアンチパターンと混同しないこと。
```

## テストしなくていいもの

- trivialなgetter/setter（`getUser()` が `this.user` を返すだけ）
- フレームワーク・ライブラリのコード（Express・ORM基本操作）
- TypeScriptの型システムが保証できるもの
- ロギング・設定値の定数

**テストすべきもの**:
- ビジネスルール・ドメインロジック
- 条件分岐・エラーハンドリング
- 外部システムとの統合ポイント
