# AI特有リスク対策ガイド

## Test Collusion（テストの共謀）

**リスク**: テストと実装を同一セッションで生成すると、AIが実装に合わせたテストを書く。
テストが「仕様の証明」ではなく「実装の追認」になりバグを見落とす。

**対策**:
1. テストを書く指示と実装を書く指示を**必ず別メッセージに分ける**
2. 重要な機能は別セッションで独立テストを生成して照合する
3. 「このテストで何を検証しているか？」を確認する

**独立検証パターン（STEP 5）**:
```
（新しいClaude Codeセッションで）
このコードのテストを書いてください。
既存のテストは見ないでください。
[実装コードをここに貼る]
```
独立生成されたテストが既存テストと一致すれば、実装が仕様通りである追加証拠になる。

## セッション境界の管理

| タイミング | 理由 |
|---|---|
| **1つの機能（BDD仕様1本）が完了したとき** | コンテキストをリセットして次を新鮮な目で始める |
| **テストスイートが全部Greenになったとき** | 完了状態でセッションを閉じると次回の起点が明確 |
| **独立検証テストを生成するとき** | 必ず新セッション。同一セッションではTest Collusionが防げない |
| **リファクタ専用作業** | 実装とリファクタを同一セッションで混在させない |

**セッション開始時の定型文**:
```
このセッションでは [機能名] をTDDで実装します。
BDD仕様: [Given/When/Thenをここに貼る]
テストコマンド: [npm test 等]
まず最初の1本のテストだけ書いてください。
```

## モッキング指針

**モックしてよいもの**:
- 外部APIサービス（課金・レート制限が発生するもの）
- メール・SMS送信（副作用が実世界に出るもの）
- 時刻・乱数（非決定的なもの）
- 外部ファイルシステム（CI環境に依存するもの）

**モックしてはいけないもの**:
- 自プロジェクト内のモジュール・クラス（実装の詳細に結合してしまう）
- データベース（ORM・クエリのバグを見逃す → テスト用DBかインメモリDBを使う）
- 内部の協調オブジェクト（リファクタ時にテストが壊れる原因になる）

**判断基準**:
```
「これをモックすると、実際の統合で起きる問題を見逃すか？」
→ YES: モックしない（実物 or インメモリDBを使う）
→ NO:  モックしてよい
```

> Claude Codeへの指示: 「DBはモックせずにインメモリDB（SQLiteやin-memory store）を
> 使ってください。内部クラスもモックせず実物を使ってください」

参考: `tdd/mocking.md`

## 要求外実装の防止

**リスク**: スコープが曖昧だとAIが勝手に機能を追加・「改善」する。

**対策**:
1. BDD仕様をプロンプト冒頭に添付する
2. 「以下の仕様のみを実装してください。追加機能は不要です」と明示する
3. 実装後にDiffを必ず確認する

## バグ密度トレンドによる上流品質の異常検知

IPA定量的管理の知見：**成功プロジェクトはバグ密度が単体 → 結合 → システムテストで減少する。**

| テスト段階 | 健全なバグ密度の傾向 |
|---|---|
| 単体テスト | 最も多い（早期に多く検出） |
| 統合テスト | 減少（単体で取り切れているから） |
| E2Eテスト | さらに少ない（ほぼゼロが理想） |

**AI駆動開発での異常パターン**：

```
⚠️ 後半テストになるほどバグが増える
   → 単体テストが「テスト通過のためだけの実装」になっている
   → Test Collusionの疑いが強い → STEP 5（独立検証）を実施する

⚠️ E2Eだけがバグを検出している
   → 上流（BDD仕様・設計）に問題がある
   → BDD仕様を見直して単体テストで防げる形に再設計する

⚠️ どの段階でもバグ密度が変わらない
   → テストが仕様を検証していない（追認テストになっている）
   → テスト内容をレビューする
```

**Claude Codeへの確認パターン**:
```
現在のバグ検出分布を教えてください：
- 単体テストで検出されたバグ数
- 統合テストで初めて検出されたバグ数
- E2Eテストで初めて検出されたバグ数

後半ほど多い場合、上流の設計または単体テストの質に問題があります。
```

## 出力のバリアント性への対応

同じ指示でも実装が変わることがある。
テストが仕様を固定する役割を担うため、テストがパスする限り実装の細部の違いは許容範囲。
重要なのはテストがパスすることであり、実装の形ではない。
