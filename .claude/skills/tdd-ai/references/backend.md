# バックエンド・API・E2Eテストパターン

## 統合テスト（APIレベル）のTDDパターン

単体テストと同じRed-Green-Refactorを、APIレイヤーで適用する。

### BDD仕様の書き方（APIレベル）

```
Feature: 注文作成API

  Scenario: 有効なカートで注文が作成できる
    Given: DBに在庫ありの商品が存在する
    When:  POST /api/orders に有効なリクエストを送る
    Then:  201レスポンスとorder_idが返る
           DBにordersレコードが作成される
```

### Claude Codeへの指示例（APIテスト）

```
以下の仕様でAPIの統合テストを書いてください。
実際のDBとHTTPクライアントを使ってください（モック禁止）。
DBはインメモリDB（SQLiteまたはテスト用DB）を使ってください。

仕様:
[BDD仕様をここに貼る]

テストを書いたらエンドポイントの実装は書かないでください。
Redを確認します。
```

### 統合テストで確認すること

```
[ ] HTTPステータスコードが正しいか
[ ] レスポンスボディの構造が正しいか
[ ] DBの状態が期待通りに変化したか
[ ] エラーケース（400/401/404/500）が正しく返るか
[ ] 副作用（メール送信・外部API）が発生しているか（必要に応じてモック）
```

## E2Eテスト（Playwrightレベル）のTDDパターン

E2Eはユーザーフローごとに1本。クリティカルなフローのみ（最大5本）。

### 対象とするフロー（例）

```
✅ E2Eにすべきもの:
  - ユーザーが新規登録からログインまで完了できる
  - カートに商品を追加して購入完了できる
  - パスワードリセットメールを受け取れる

❌ E2Eにしないもの:
  - 個別のフォームバリデーション（単体テストで十分）
  - 管理画面の細かい操作（統合テストで十分）
```

### E2Eテストの逆順アプローチ（Green→Red）

```
1. まず手動で動作確認したフローをPlaywrightで記録する
2. 実装が変わったときにRedになることを確認する
3. 実装修正でGreenに戻す
```

### Claude Codeへの指示例（Playwright）

```
以下のユーザーフローをPlaywrightでE2Eテストとして書いてください。

フロー: [具体的な操作手順をここに書く]
起動コマンド: [npm run dev 等]
テストコマンド: npx playwright test

ユーザーの操作（クリック・入力）と期待される結果（URL・表示テキスト）に
フォーカスしてください。CSSクラスや内部状態はテストしないでください。
```

## DB・データ層のテストパターン

```
# DBテストの基本方針
- 各テストは独立したDBステートで始める（teardown必須）
- トランザクションを使ってテスト後にロールバックする
- シードデータはファクトリ関数で生成する（ハードコード禁止）

# Claude Codeへの指示
「テストのセットアップで実際のDBを使い、
teardownでデータを削除してください。
ファクトリ関数でテストデータを生成してください。
SQLのmigrationも必要に応じて作成してください。」
```
