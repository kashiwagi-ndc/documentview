## カテゴリ別必須要素

各カテゴリで「これを聞かないとプロンプト品質が落ちる」要素。

### 1. 文章生成系
- **必須**: 目的 / 役割 / 背景 / 出力形式（字数・トーン・構成）
- **強く推奨**: 読者層、媒体
- **任意**: 例、NG表現、参考スタイル

### 2. コード/技術系
- **必須**: 役割 / 言語・バージョン / ライブラリ・FW / 入出力例
- **強く推奨**: 既存コードの有無、テスト要件
- **任意**: コーディング規約、性能要件

### 3. 分析/思考系
- **必須**: 役割 / 分析対象 / 観点（軸） / 出力構造（表/箇条書き/ロジックツリー等）
- **強く推奨**: 結論の形式、判断基準
- **任意**: 参考フレームワーク（SWOT、3C等）

### 4. 対話/RP系
- **必須**: 役割（人物像詳細） / 口調 / NG行動 / 目的
- **強く推奨**: 会話の長さ、応答パターン
- **任意**: 背景設定、世界観

### 5. 教育/学習系
- **必須**: 役割 / 対象レベル / 学習目標 / 例題の有無
- **強く推奨**: 前提知識、学習スタイル
- **任意**: ペース、評価方法

### 6. リサーチ/競合調査系
- **必須**: 役割 / 調査対象 / 比較軸 / 出典指示 / 鮮度
- **強く推奨**: 目的（提案書 / 機能設計 / 技術選定 等）、網羅性
- **任意**: 出力フォーマット詳細、参考情報源
- **特殊**: 「結果の活用方法」を聞いて3出口（A/B/C）に分岐

### 7. 設計書/ドキュメント系
- **必須**: 役割 / 対象システム / ドキュメント種別 / 読み手 / 章立て or 規約準拠
- **強く推奨**: 既存資料の有無、用語統一
- **任意**: 図表の有無、テンプレファイル

### 8. インフラ/アーキ設計系
- **必須**: 役割 / 対象環境（AWS/Azure/GCP/オンプレ） / 要件（SLA・コスト・コンプラ） / 読み手 / 出力フォーマット
- **強く推奨**: 既存構成、制約事項
- **任意**: 採用根拠の必須化、構成図フォーマット

### 9. 業務文書系
- **必須**: 役割 / 文書種別 / 読み手 / 出力構成 / 結論
- **強く推奨**: トーン（社内/社外）、文字数、数値根拠
- **任意**: 体裁テンプレ、参考過去資料

### 10. 顧客コミュニケーション系
- **必須**: 役割 / 状況・目的 / 読み手（役職・関係性） / トーン / 次アクション
- **強く推奨**: NG表現除外、結論明確化
- **任意**: 過去の経緯、補足資料

### 11. 運用/トラブル系
- **必須**: 役割 / 対象システム / 文書種別（手順書/Runbook/ポストモーテム） / 読み手レベル
- **強く推奨**: 手順番号、想定エラーと対処、ロールバック手順
- **任意**: 再発防止、関連ツール

### 12. リバースエンジニアリング系
- **必須**: 役割 / 入力種別（コード/API/DB/ログ/バイナリ） / 復元レベル / 出力フォーマット / **確度表記の強制**
- **強く推奨**: 既存資料の有無、対象技術（言語/プラットフォーム）
- **任意**: 段階的復元の段階指定

### 13. DB/SQL系
- **必須**: 役割 / **DBエンジン・バージョン** / 用途（生成/最適化/設計/移行） / テーブル定義 or DDLアクセス方法 / 出力フォーマット
- **強く推奨**: インデックス情報、データ量
- **特殊**: 破壊系SQLは安全装置を自動付与
- **任意**: 性能要件、制約

### 14. 要件ヒアリング/上流系
- **必須**: 役割 / フェーズ（事前/当日/事後） / プロジェクト種別 / 業界 / ヒアリング相手
- **強く推奨**: 現状理解度、既知の制約
- **任意**: 業界特有の留意点

### 15. その他/自由
- **必須**: 役割 / 背景 / 出力形式
- ユーザーの説明に基づき柔軟にヒアリング

## カテゴリ判定の優先順位

複数カテゴリに該当しそうな場合の優先順位：

1. **明示的な業務系キーワード** > 一般用途
   - 例: 「障害報告メール」→ 顧客コミュニケーション系（メール=文章生成 ではない）
2. **特殊要件あり** > 一般カテゴリ
   - 例: 「PostgreSQLのSQL作って」→ DB/SQL系（コード系 ではない）
3. **複合的な場合は主目的で判定**
   - 例: 「競合アプリの調査結果をブログ記事に」→ リサーチ系で出口Cに分岐
4. **不明な場合は確認**
   - カテゴリ一覧から選択してもらう

## MVPテンプレートライブラリ（25個）

各カテゴリの定番テンプレ。`templates/` ディレクトリに格納（フェーズ2で作成）。

### 業務文書系（5個）
- `proposal-draft.md` — 提案書ドラフト
- `progress-report.md` — 進捗報告メール
- `meeting-minutes.md` — 議事録整理
- `code-review.md` — コードレビュー依頼
- `blog-article.md` — ブログ記事作成（writing-crew-starter連携）

### 顧客コミュニケーション系（1個）
- `incident-report-external.md` — 障害一次報告（社外向け）

### 運用/トラブル系（1個）
- `postmortem.md` — ポストモーテム

### 設計書/ドキュメント系（1個）
- `api-spec.md` — API仕様書

### リサーチ系（2個）
- `competitor-analysis.md` — 競合アプリ比較（ai-employee連携）
- `tech-selection.md` — 技術選定比較

### リバースエンジニアリング系（5個）
- `reverse-code-to-flow.md` — コード→処理フロー復元
- `reverse-code-to-sequence.md` — コード→シーケンス図
- `reverse-db-to-er.md` — DB→ER図/テーブル定義書
- `reverse-api-to-spec.md` — API挙動→仕様書
- `reverse-code-to-design.md` — コード→基本設計書ドラフト

### DB/SQL系（5個）
- `sql-generation.md` — SQL生成（集計・分析系）
- `sql-optimization.md` — スロークエリ最適化
- `db-design.md` — テーブル/ER設計
- `data-migration.md` — データ移行スクリプト
- `sql-reverse.md` — 既存SQL解析（リバース）

### 要件ヒアリング系（5個）
- `hearing-preparation.md` — ヒアリング事前準備
- `hearing-questions.md` — 質問リスト生成（業界別）
- `hearing-workflow.md` — 業務フロー聞き取り
- `hearing-non-functional.md` — 非機能要件ヒアリング
- `hearing-post-organize.md` — ヒアリング議事録→要件整理

## 業界別ノウハウ（要件ヒアリング系で参照）

| 業界 | 特に聞くべきこと | センシティブで段階的に聞くこと |
|---|---|---|
| **金融** | 規制対応（個人情報・FISC）、監査要件、システム連携 | 内部統制の現状（直球で聞かない） |
| **製造** | 既存システム連携（生産管理・PLM）、現場運用 | 現場の暗黙ルール（観察重視） |
| **流通/小売** | 季節変動・繁忙期、店舗運用、POS連携 | 在庫差異・廃棄の実態 |
| **医療** | 個人情報・電子カルテ規格（HL7/FHIR）、薬機法 | 患者情報の取扱い（細心の注意） |
| **公共** | 調達ルール・既存契約、システム間連携 | 政治的背景（明示的に聞かない） |
| **SaaS/Web** | スケール・SLA・マルチテナント、API連携 | 競合への配慮 |
