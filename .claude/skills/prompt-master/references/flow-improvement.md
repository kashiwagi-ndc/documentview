# 改善モード フロー詳細

ユーザーが持ち込んだ既存プロンプトを診断し、改善版を提示するフロー。

---

## 1. モード突入条件

- ユーザーが「このプロンプトを改善して」「プロンプトを直して」等を発した
- かつ既存プロンプト本文がコードブロック or 引用形式で提示されている

---

## 2. フロー全体

```
1. 既存プロンプトの解析
2. カテゴリ推定
3. 診断レポート生成
4. 不足情報のヒアリング（必要時のみ）
5. 確認CP（必須）
6. 改善版プロンプト提示（差分明示つき）
7. イテレーション
8. 「完成」で最終版整理
```

---

## 3. 各ステップ詳細

### Step 1: 既存プロンプトの解析

提示されたプロンプトを構造的に分析する。

#### 分析観点

| 観点 | チェック内容 |
|---|---|
| **必須3要素** | 役割 / 背景 / 出力形式 が揃っているか |
| **カテゴリ別必須要素** | 該当カテゴリに必要な要素が含まれているか |
| **構造の明確さ** | 見出しで区切られているか、文章が混ざっていないか |
| **冗長性** | 同じことを繰り返していないか |
| **曖昧表現** | 「うまく」「いい感じに」等の主観的指示がないか |
| **指示の競合** | 矛盾する指示がないか |
| **読み手指定** | 業務系プロンプトで読み手が明確か |
| **出力形式** | 形式・分量・構造が具体的に指定されているか |
| **例示** | 必要な箇所に例があるか |
| **NG事項** | 避けるべき内容が明示されているか |
| **コピペ性** | コードブロック整形されているか |

### Step 2: カテゴリ推定

既存プロンプトの内容からカテゴリを推定。`references/categories.md` の判定基準に従う。
ユーザーが明示していれば優先。

### Step 3: 診断レポート生成

改善モードの特徴的な出力。以下のフォーマットで提示。

```markdown
🔍 診断レポート

【現状評価】カテゴリ: 〇〇系として診断

✅ 良い点
  - [評価できる要素]
  - [評価できる要素]

⚠️ 改善が必要な点
  - [問題1]: [なぜ問題か] → 改善案: [〇〇]
  - [問題2]: [なぜ問題か] → 改善案: [〇〇]
  - [問題3]: [なぜ問題か] → 改善案: [〇〇]

📊 不足している要素
  - [要素1]（カテゴリ別必須）: [なぜ必要か]
  - [要素2]（推奨）: [なぜ必要か]

📈 推定精度向上度: [低→中 / 中→高 / 高→さらに高]

【次のステップ】
不足情報をヒアリングします（[N]問）。それから改善版を提示します。
```

### Step 4: 不足情報のヒアリング

診断で不足が見つかった要素を順番に聞く。

- 既存プロンプトに記載のある情報は再質問しない
- 1問ずつ
- 業務系の「読み手」が未指定なら必ず聞く

### Step 5: 確認CP（必須）

改善モードでは必ずCPを実施。

```markdown
📋 改善方針まとめ

【元のプロンプト】カテゴリ: 〇〇系

【主な改善方針】
  1. [改善ポイント1]: [具体的にどう変える]
  2. [改善ポイント2]: [具体的にどう変える]
  3. [改善ポイント3]: [具体的にどう変える]

【追加する要素】
  - 〇〇
  - 〇〇

【削除/変更する要素】
  - 〇〇 → 〇〇

この方針で改善版を作成します。
よろしければ「OK」、調整があれば指摘してください。
```

### Step 6: 改善版プロンプト提示

3層構造に従って構築し、必ず差分を明示する。

```markdown
✅ 改善版プロンプトを生成しました。

【改善版プロンプト（v1）】

```text
[改善版の本体]
\```

🔄 元のプロンプトからの主な変更点:
  - 【役割】 〇〇 → 〇〇（理由: 〇〇）
  - 【背景】 追加: 〇〇（理由: 〇〇）
  - 【読み手】 新規追加（理由: 業務系で必須）
  - 【出力形式】 〇〇 → 〇〇（理由: 具体性向上）
  - 【NG事項】 新規追加（理由: 〇〇）

【改善のポイント】
- [なぜこの改善が効くか1]
- [なぜこの改善が効くか2]

【元のプロンプトでよかった点（維持）】
- 〇〇
- 〇〇

💡 オプション:
  - 英語版が欲しい場合: 「英語版もください」
  - 元との比較表が欲しい場合: 「比較表で」
  - プレーン版が欲しい場合: 「プレーン版で」
```

### Step 7: イテレーション

`flow-creation.md` のStep 7と同じ。

3レーン振り分け：
- 微調整: 即時修正＋差分明示
- 要素編集: 該当セクション編集＋差分明示
- 方針転換: 確認CP再実施

### Step 8: 「完成」明示区切り

```markdown
✅ 完成です。最終版を整理してお渡しします。

【最終版プロンプト】
[コードブロック]

【改善の総括】
- 元のプロンプトの状態: 〇〇
- 改善後の状態: 〇〇
- 推定精度向上: 〇〇 → 〇〇

【今後のプロンプト設計のヒント】
- [一般化できる学び1]
- [一般化できる学び2]

このプロンプトを定番化したい場合は「定番化して」とお伝えください。
```

「今後のプロンプト設計のヒント」を入れるのが改善モード独自の付加価値。
**ユーザー自身のプロンプト力が育つ**ことを意識した出力にする。

## 4. 診断時の典型的な問題パターン

### パターンA: 役割が曖昧 or 未指定

```
元: 「美味しいレシピを教えて」
問題: 役割未指定。誰の視点か不明。
改善: 「あなたは和食料理人の経験20年のシェフです」
```

### パターンB: 背景情報の不足

```
元: 「コードレビューして」
問題: 言語・FW・コンテキスト不明
改善: 言語・バージョン・ライブラリ・コーディング規約を追加
```

### パターンC: 出力形式が曖昧

```
元: 「うまくまとめて」
問題: 構造・分量・スタイル不明
改善: 「Markdown形式 / 500字以内 / 3章構成（背景・現状・提案）」
```

### パターンD: 読み手未指定（業務系で致命的）

```
元: 「障害報告書作って」
問題: 読み手不明。社内向け？顧客向け？
改善: 「読み手: 顧客の情報システム部長」を追加し、トーンを最適化
```

### パターンE: 主観的指示

```
元: 「いい感じに書いて」「うまく作って」
問題: 評価基準不明
改善: 「具体性・正確性・簡潔さを重視」「文末は敬体」等の客観的指示
```

### パターンF: 例の不足

```
元: 「JSONで返して」
問題: スキーマ不明
改善: 入出力例を含める
```

### パターンG: 指示の競合

```
元: 「簡潔に詳しく書いて」
問題: 矛盾
改善: 「結論を最初に1文、その後詳細を箇条書きで」等で解消
```

### パターンH: 構造化されていない

```
元: 1段落の長文プロンプト
問題: AIが優先度を読み取りにくい
改善: 見出しで区切る（# 役割 / # 背景 / # タスク / # 出力形式）
```

## 5. リサーチ系プロンプトの改善特有のチェック

カテゴリ6（リサーチ系）の場合は追加で：

- 出典指示があるか
- 鮮度の指定があるか
- 比較軸が明確か
- 「差別化軸の必須化」が入っているか
- スコープ縮退ガード（網羅性制限）があるか

---

## 6. リバースエンジニアリング系プロンプトの改善特有のチェック

カテゴリ12（リバース系）の場合は追加で：

- **確度表記の強制**が含まれているか（最重要）
- 入力種別が明確か
- 復元レベルが指定されているか
- 不明な点を「不明」と書く許可が与えられているか

---

## 7. DB/SQL系プロンプトの改善特有のチェック

カテゴリ13（DB/SQL系）の場合は追加で：

- **DBエンジン・バージョン**の指定があるか（最重要）
- テーブル定義へのアクセス方法が明確か
- 破壊系SQLの安全装置が組み込まれているか
- 性能要件（パフォーマンス系の場合）が含まれているか
