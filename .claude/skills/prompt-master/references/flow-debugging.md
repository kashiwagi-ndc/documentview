# 壁打ちモード フロー詳細

ユーザーが「このプロンプトでこういう結果になった、どう直せばいい？」と相談してきた時のフロー。
プロンプト＋実出力＋期待結果の3点から逆算して修正する、デバッグ的なアプローチ。

---

## 1. モード突入条件

ユーザーから以下の3点が揃って提示されている：

1. **既存プロンプト本文**（試したプロンプト）
2. **実際の出力**（うまくいかなかった結果）
3. **期待した結果**（こうあってほしかった、の説明）

3点が揃っていなくても、ユーザーが「うまく動かなかった」「期待と違った」等のキーワードを含めれば壁打ちモードに突入。

---

## 2. フロー全体

```
1. 3点セットの収集（揃っていない場合は聞く）
2. ギャップ分析（実出力 vs 期待結果）
3. 原因仮説の生成
4. 修正方針の提案
5. 確認CP（必須）
6. 修正版プロンプト提示
7. 「もう一度試して結果を貼って」のループ受付
8. 「完成」で最終版整理
```

---

## 3. 各ステップ詳細

### Step 1: 3点セットの収集

以下のいずれかが欠けていれば必ず聞く：

```
壁打ちモードで進めます。デバッグのために以下を教えてください：

1. ✅ 試したプロンプト ← [既に提示済み / 未提示]
2. ✅ 実際にAIから返ってきた出力 ← [既に提示済み / 未提示]
3. ✅ 本当はどうなってほしかったか ← [既に提示済み / 未提示]

不足している項目を共有してください。
```

特に「期待した結果」は曖昧になりがちなので、具体例を求める：

```
「期待した結果」をもう少し詳しく教えてください。
たとえば「もっと簡潔に」だけでなく、
「3行以内で / 結論先出し / 数値を含む」のように具体的だと診断しやすいです。
```

### Step 2: ギャップ分析

実出力と期待結果の差を構造的に分析する。

#### 分析観点

| 観点 | 例 |
|---|---|
| **構造のズレ** | 期待は箇条書き、実出力は文章 |
| **分量のズレ** | 期待は500字、実出力は2000字 |
| **トーンのズレ** | 期待は丁寧、実出力はカジュアル |
| **抽象度のズレ** | 期待は具体例つき、実出力は一般論 |
| **観点のズレ** | 期待した観点が欠けている、不要な観点が混入 |
| **正確性のズレ** | 期待した事実と違う、推測を断定で書いている |
| **形式のズレ** | JSON期待でMarkdown、表期待で散文 |
| **言語のズレ** | 日本語期待で英語混在 |

### Step 3: 原因仮説の生成

ギャップから、プロンプトのどこに問題があったかを仮説化。

#### 典型的な原因パターン

| 症状 | 想定原因 |
|---|---|
| 出力が冗長 | 字数指定なし / 「詳しく」と「簡潔に」が両方ある |
| 観点が違う | 観点（軸）が明示されていない |
| 一般論しか出ない | 例示なし / 対象が抽象的 |
| 推測を断定で書く | 確度表記の指示がない（リバース系の典型） |
| 構造がバラバラ | 出力形式の構造指定なし |
| 言葉遣いが想定外 | 読み手未指定 / トーン指定なし |
| 事実と違うことを書く | 出典指示なし / 検証指示なし |
| 不要な前置きが長い | 「前置き不要」の指示がない |

### Step 4: 修正方針の提案

```markdown
🔍 ギャップ分析

【期待 vs 実出力】
| 観点 | 期待 | 実出力 | ギャップ |
|---|---|---|---|
| 〇〇 | 〇〇 | 〇〇 | 〇〇 |

【原因仮説】
1. [原因仮説1]: [根拠]
2. [原因仮説2]: [根拠]

【修正方針】
  1. 【〇〇】 を追加: [理由]
  2. 【〇〇】 を変更: [理由]
  3. 【〇〇】 を削除: [理由]

この方針で修正版を作成します。
```

### Step 5: 確認CP（必須）

壁打ちモードでは必ずCPを実施。ユーザーの認識とズレていないか確認。

```markdown
📋 修正方針まとめ

【あなたが直面した問題】
[要約]

【原因の見立て】
[原因仮説]

【修正方針】
  1. 〇〇
  2. 〇〇
  3. 〇〇

この理解で合っていますか？
合っていれば「OK」、認識が違うようなら指摘してください。
```

### Step 6: 修正版プロンプト提示

```markdown
✅ 修正版プロンプトを生成しました。

【修正版プロンプト（v1）】

```text
[修正版の本体]
\```

🔄 元のプロンプトからの修正点:
  - 【〇〇】 追加（理由: ギャップ「〇〇」の解消）
  - 【〇〇】 変更（理由: ギャップ「〇〇」の解消）

【次のステップ】
このプロンプトを試して、結果を貼り付けてください。
期待通りなら「完成」、まだズレがあれば具体的に指摘してください。
さらに調整します。
```

### Step 7: 「もう一度試して結果を貼って」のループ

壁打ちモード独自の特徴。実出力ベースで反復改善する。

```
ユーザー: 「試したらまだ〇〇な結果になった」

→ Step 2（ギャップ分析）に戻る
→ 新しいギャップを分析
→ 修正方針提案
→ 修正版提示
```

最大3〜4回のループまで継続。それを超えても収束しない場合は：

```
💡 何度か試行していますがズレが残っています。
   いったん「作成モード」でゼロから設計し直しませんか？
   「ゼロから作って」とお伝えいただければ、新規ヒアリングから始めます。
```

### Step 8: 「完成」明示区切り

```markdown
✅ 完成です。期待通りの結果が出るようになりました。

【最終版プロンプト】
[コードブロック]

【デバッグの記録】
- 当初の問題: 〇〇
- 原因: 〇〇
- 解決策: 〇〇

【今回のデバッグから学べること】
- [プロンプト設計の一般化できる教訓1]
- [プロンプト設計の一般化できる教訓2]

このプロンプトを定番化したい場合は「定番化して」とお伝えください。
```

---

## 4. 壁打ちモードの強み

このモードは**「プロンプトエンジニアリングのデバッグ術」**として機能する。

### 利点

- **実出力という客観的事実から逆算**するので、曖昧な指摘ではなく具体的な修正ができる
- ユーザーが**「なぜ期待通りにならなかったか」を言語化**できる
- AIの**ハルシネーション傾向や弱点**が見えるので、次回以降の予防になる
- コードのデバッグと同じ感覚で**反復的改善**ができる

### 技術職向けの相性

エンジニアにとって「コードは動くが期待通りでない」状態のデバッグは日常作業。
プロンプトも同じ感覚で扱える点が刺さる。

---

## 5. 典型ケース別の対応

### ケースA: コード生成で動かない

```
ユーザー: 「このコード生成プロンプトで動かないコードが出てきた」

ギャップ分析: 言語/FWバージョンの指定漏れ
→ 修正: 環境情報を明示する形に
```

### ケースB: 要約が期待と違う

```
ユーザー: 「要約させたら細かすぎる / 大雑把すぎる」

ギャップ分析: 字数・粒度の指定漏れ
→ 修正: 「200字 / 主要3ポイント / 結論先出し」等の具体的な構造指定
```

### ケースC: リサーチ結果が浅い

```
ユーザー: 「競合調査させたら表面的な情報しか出てこなかった」

ギャップ分析: 出典指示・深掘り指示・観点指定が弱い
→ 修正: 出典URL必須・観点ごとの深掘り指示・「不明は不明と書く」許可
```

### ケースD: 文体が想定外

```
ユーザー: 「メール文を作らせたら堅すぎる / カジュアルすぎる」

ギャップ分析: 読み手・トーンの指定漏れ
→ 修正: 読み手の役職・関係性・希望トーンを明示
```

### ケースE: 推測を断定で書く

```
ユーザー: 「コード解析させたら『多分こうです』と断定的に書かれて間違ってた」

ギャップ分析: 確度表記の強制不足（リバース系の典型）
→ 修正: [確定]/[推測]/[要確認] タグの強制と、不明は不明と書く指示
```
