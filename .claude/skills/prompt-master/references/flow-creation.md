# 作成モード フロー詳細

ゼロからプロンプトを設計するときのフロー。

---

## 1. モード突入条件

- ユーザーが「〇〇のプロンプト作って」「〇〇用のプロンプトが欲しい」等
- 既存プロンプト本文の提示なし
- 実出力・期待結果の提示なし

---

## 2. フロー全体

```
1. カテゴリ自動推定
2. カテゴリ確認（短く）
3. テンプレ該当チェック → 該当なら「テンプレ短縮ルート」を提案
4. ヒアリング（1問ずつ・カテゴリ別必須要素から）
5. 条件付きCP（中間チェックポイント）
6. プロンプト本体提示（3層構造）
7. イテレーション受付
8. 「完成」で最終版整理
```

---

## 3. 各ステップ詳細

### Step 1: カテゴリ自動推定

ユーザーの初回発話から、`references/categories.md` の判定キーワードを参照してカテゴリ番号を推定する。

**推定例**:
- 「障害報告メール作って」→ カテゴリ10（顧客コミュニケーション系）
- 「PostgreSQLのSQL作って」→ カテゴリ13（DB/SQL系）
- 「競合アプリ調査」→ カテゴリ6（リサーチ系）
- 「要件ヒアリングの事前準備」→ カテゴリ14（要件ヒアリング系）

### Step 2: カテゴリ確認

短く宣言してすぐ次へ進む（ユーザーの応答を待たない）。

```
「[〇〇系]として進めますね（違ったらお知らせください）」
```

カテゴリ判定が複数候補で迷う場合のみ、明示的に選択肢を出す：

```
複数のカテゴリに該当しそうです。どれが近いですか？
  A) 〇〇系
  B) 〇〇系
  C) その他/自由
```

### Step 3: テンプレ該当チェック

カテゴリ内に定番テンプレ（`templates/*.md`）が該当する場合、短縮ルートを提案：

```
定番テンプレ「[テンプレ名]」が使えます。

  - 「テンプレで」 → 3問だけで完成
  - 「ゼロから」   → 通常ヒアリング

どちらにしますか？
```

該当しない場合はそのままStep 4へ。

### Step 4: ヒアリング

#### ルール
- **1問ずつ**（複数質問の同時投げ禁止）
- カテゴリ別必須要素（`references/categories.md`）から順に
- ユーザーの初回発話で既に分かっている情報は再質問しない
- 業務系（7〜11, 14）は「読み手」を必ず聞く

#### ヒアリングの順序

優先順位（共通）：
1. 目的（最重要）
2. 対象/題材
3. 役割設定（未指定なら推奨を提示）
4. 背景・前提
5. 出力形式
6. 読み手（業務系で必須）
7. カテゴリ別必須要素（DBエンジン、復元レベル、調査範囲など）
8. 任意要素（制約、例、評価基準、NG事項）

#### 質問テンプレ

```
[これまでの理解]
- 目的: 〇〇
- カテゴリ: 〇〇系

[次に確認したい点]
〇〇について教えてください。
（補足: このカテゴリだと△△を決めると精度が上がります）
```

#### ヒアリング項目数のガイドライン

- 一般用途（カテゴリ1〜5）: 3〜5項目
- リサーチ系（6）: 4〜6項目
- 業務系（7〜11, 14）: 5〜8項目
- リバース系（12）・DB/SQL系（13）: 5〜7項目

### Step 5: 条件付きCP

以下のいずれかに該当する場合、確認CPを必ず実施：

- ヒアリング項目4個以上
- 業務系カテゴリ（7〜11, 14）
- リサーチ系で出口B/C選択時
- リバース系・DB/SQL系の全ケース

シンプル用途（一般用途で3項目以下）はCPをスキップ。

#### CP統一フォーマット

```markdown
📋 ヒアリング結果まとめ

【カテゴリ】〇〇系
【役割】〇〇
【背景】〇〇
【対象】〇〇
【出力形式】〇〇
【読み手】〇〇（業務系の場合）
【カテゴリ別要素】
  - 〇〇: 〇〇
【制約・補足】〇〇

💡 追加で入れることも可能な要素:
  - [品質チェックリストから自動抽出]
  - [品質チェックリストから自動抽出]

この内容でプロンプトを構築します。
よろしければ「OK」、修正があれば指摘してください。
```

#### 追加要素の主体提案

`references/quality-checklist.md` から、まだヒアリングしていない要素を抽出して提示する。
ユーザーが必要と判断すれば追加ヒアリング、不要なら「OK」で確定。

### Step 6: プロンプト本体提示

`references/core-template.md` の3層構造に従って構築。

```
✅ プロンプトを生成しました。

【コピペ用プロンプト】

```text
# 役割
...

# 背景・前提
...

# タスク
...

# 出力形式
...

# [カテゴリ別Layer 2要素]
...
\```

【プロンプトの意図】
- 役割を「〇〇」にした理由: 〇〇
- 背景に「〇〇」を含めた理由: 〇〇

【使い方のコツ】
- 〇〇のように使うと精度が上がります
- 失敗パターン: 〇〇 → 調整方法: 〇〇

💡 オプション:
  - 英語版が欲しい場合: 「英語版もください」
  - バイリンガル版が欲しい場合: 「バイリンガル版で」
  - プレーン版が欲しい場合: 「プレーン版で」
  - 定番化したい場合: 「定番化して」
```

### Step 7: イテレーション

ユーザーからのフィードバックを受け付ける。

修正タイプの自動判定：

| タイプ | 発話例 | 対応 |
|---|---|---|
| 微調整 | 「字数300字」「トーン柔らかく」 | 即時修正＋差分明示 |
| 要素編集 | 「例も追加」「制約はいらない」 | 該当セクション編集＋差分明示 |
| 方針転換 | 「読み手変えたい」「カテゴリ違う」 | 確認CP再実施 |

#### 修正版提示フォーマット

```
🔄 v2 の変更点:
  - 【〇〇】変更前 → 変更後
  - 【〇〇】追加: 〇〇
  - 【〇〇】削除

【コピペ用プロンプト v2】
[コードブロック]
```

#### 迷走警告（4回目）

```
💡 何度か修正を重ねています。
   方向性そのものを見直したい場合は「いったんリセット」とお伝えください。
   再ヒアリングから始めます。
```

### Step 8: 「完成」明示区切り

ユーザーが「完成」「OK、これで」「確定」等を発した時、最終版を整理：

```
✅ 完成です。最終版を整理してお渡しします。

【最終版プロンプト】
[コードブロック]

【プロンプトの解説】
- なぜこの構成にしたか
- 使い方のコツ
- 想定される失敗パターンとその時の調整方法

このプロンプトを定番化したい場合は「定番化して」とお伝えください。
templates/ に保存します。
```

## 4. 業務シナリオ例

### 例A: 障害一次報告メール

```
ユーザー: 「お客様向けに障害一次報告メールのプロンプトを作って」

→ Step 1: カテゴリ10（顧客コミュニケーション系）と推定
→ Step 2: 「顧客コミュニケーション系として進めます」
→ Step 3: テンプレ "incident-report-external.md" 該当 → 短縮ルート提案
   ユーザーがテンプレで進めると選択
→ Step 4-5: 3問のヒアリング（読み手の役職、影響範囲、復旧見込み）+ CP
→ Step 6: プロンプト本体提示
→ Step 7: 必要に応じイテレーション
→ Step 8: 「完成」で最終版整理
```

### 例B: 競合アプリ調査

```
ユーザー: 「タスク管理アプリの競合調査プロンプトが欲しい」

→ Step 1: カテゴリ6（リサーチ系）と推定
→ Step 2: 「リサーチ/競合調査系として進めます」
→ Step 3: テンプレ "competitor-analysis.md" 該当 → 短縮ルート提案
→ Step 4-5: 3出口（A/B/C）の選択を含むヒアリング + CP
   - B選択時: ai-employee用起動文を生成
→ Step 6: プロンプト本体（または起動文）提示
→ Step 7-8: イテレーション → 完成
```

## 5. エッジケース対応

### ユーザーが情報を出し惜しむ場合

```
ユーザー: 「全部任せます」

→ 仮の役割・背景でドラフトを出してから調整する旨を伝える
→ 「いったん一般的な前提でドラフトを作りますね。提示後に調整してください」
```

### カテゴリが推定できない場合

```
プロンプトマスター: 「ご要望をもう少し詳しく教えてください。
                  
                  該当しそうなカテゴリ:
                  A) 〇〇系
                  B) 〇〇系
                  C) その他/自由
                  
                  どれが近いですか？」
```

### ヒアリングが4往復しても要件が固まらない

```
プロンプトマスター: 「いったん仮置きでプロンプトを出してから磨きますか？」
```

ユーザーがYesなら仮版を提示してイテレーションで磨く方針に切り替え。
