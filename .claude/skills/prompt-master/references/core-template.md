# プロンプト本体テンプレート（3層構造）

すべての生成プロンプトはこのテンプレートに従って構築する。

---

## 構造概要

```
【Layer 1: コア】 全カテゴリ必須
  - 役割
  - 背景
  - 出力形式

【Layer 2: カテゴリ別必須】 自動追加
  - カテゴリに応じて追加（下記参照）

【Layer 3: 任意】 必要時のみ追加
  - 制約 / 例 / 評価基準 / NG事項 / 参考資料
```

---

## Layer 1: コアテンプレート

すべてのプロンプトに必須。

```markdown
# 役割
あなたは[専門領域]の[年数や経験を示す形容詞]な[専門家像]です。
[必要なら追加の役割属性 — 価値観・思考スタイル・口調等]

# 背景・前提
- [前提条件1]
- [前提条件2]
- [既知情報]
- [読み手や利用シーン]

# タスク
[何をしてほしいかを明確に1〜2文で]

# 出力形式
- 形式: [Markdown / HTML / 表 / 箇条書き / JSON 等]
- 長さ: [字数・項目数の目安]
- 構成: [章立て・順序]
- スタイル: [トーン・敬体常体・専門用語の扱い]
```

## Layer 2: カテゴリ別必須要素

カテゴリ別に以下を追加。

### 文章生成系（カテゴリ1）

```markdown
# 想定読者
[読者層 / 知識レベル / 関心事]

# トーン・スタイル
- [敬体/常体]
- [親しみやすさ/論理的/感情的 等]
```

### コード/技術系（カテゴリ2）

```markdown
# 技術スタック
- 言語: [言語とバージョン]
- フレームワーク/ライブラリ: [名称とバージョン]
- ランタイム: [Node 20 / Python 3.12 等]

# 入出力例
入力例:
[実例]

期待される出力例:
[実例]

# 動作要件
- [テスト要件]
- [互換性要件]
```

### 分析/思考系（カテゴリ3）

```markdown
# 分析の観点（軸）
1. [観点1]
2. [観点2]
3. [観点3]

# 出力構造
[比較表 / SWOT / ロジックツリー / 箇条書き 等の指定]

# 結論の形式
[判断 / 推奨 / 評価点 / 次アクション 等]
```

### 対話/RP系（カテゴリ4）

```markdown
# 人物像
- 名前/呼び方: [〇〇]
- 性格: [〇〇]
- 専門領域: [〇〇]
- 価値観: [〇〇]

# 口調・話し方
[具体的な口調の例 — 「〜だぜ」「〜ですわ」等]

# やってはいけないこと（NG行動）
- [〇〇は言わない]
- [〇〇は推奨しない]
```

### 教育/学習系（カテゴリ5）

```markdown
# 学習者プロファイル
- レベル: [初心者 / 中級者 / 上級者]
- 前提知識: [〇〇は知っている / 知らない]
- 学習目標: [〇〇できるようになる]

# 教え方の方針
- [例題の使い方]
- [難易度の段階づけ]
- [質問への応答方針]
```

### リサーチ/競合調査系（カテゴリ6）

```markdown
# 調査範囲
- 対象: [〇〇社 / 〇〇カテゴリ]
- 地域: [国内 / グローバル]
- 期間: [直近1年 / 全期間]

# 比較軸
1. [機能/価格/UX/対象ユーザー等]
2. [〇〇]
3. [〇〇]

# 出典の扱い
- 各項目に出典URLを必ず明記
- 公式情報を優先
- レビューサイト（G2/Capterraなど）も参照
- 不確実な情報は「[要確認]」とマークすること

# 鮮度
[直近X年の情報を優先 / 最新リリースまで反映]

# 網羅性
- 上位[N]社を詳述、それ以外は名前のみ列挙
- 主要機能TOP[M]に絞って比較

# 差別化軸の必須化
比較表だけで終わらせず、「結局どこが違うのか」「自社が勝つならどこか」の差別化軸を必ず出力に含めること。
```

### 設計書/ドキュメント系（カテゴリ7）

```markdown
# 読み手
[顧客部長 / 自社マネージャー / 開発チーム 等]

# ドキュメント種別
[要件定義書 / 基本設計書 / 詳細設計書 / API仕様書 等]

# 章立て
1. [章1]
2. [章2]
...

# 用語統一
- [専門用語の表記ルール]
- [略語の扱い]
```

### インフラ/アーキ設計系（カテゴリ8）

```markdown
# 対象環境
[AWS / Azure / GCP / オンプレ / マルチクラウド]

# 要件
- SLA: [99.9%等]
- コスト: [月額予算]
- コンプライアンス: [〇〇準拠]

# 読み手
[顧客技術部 / 経営層 / 自社運用チーム]

# 出力フォーマット
- 構成図: [Mermaid / drawio形式の説明]
- 各サービスの採用根拠を必ず併記
```

### 業務文書系（カテゴリ9）

```markdown
# 読み手
[役職・部門・関係性を明確に]

# 文書種別
[提案書 / 見積根拠 / 議事録 / WBS / 報告書]

# 構成
- 結論先出し（[要旨/結論を冒頭に]）
- [章立て]

# トーン
[社内 / 社外 / 役員向け 等]

# 数値根拠
[数値を入れる箇所には必ず根拠を併記]
```

### 顧客コミュニケーション系（カテゴリ10）

```markdown
# 読み手
- 役職: [〇〇部長 / 現場担当 等]
- 関係性: [初対面 / 既知 / 長期取引先]
- 技術背景: [あり / なし]

# 状況
[何があって、何を伝えるか]

# 目的
[謝罪 / 報告 / 依頼 / 調整 等]

# トーン
[丁寧 / 緊急 / 丁重 / フォーマル]

# 必須要素
- 結論明確化
- 次アクション提示
- [必要なら謝罪表現]

# NG表現
- [使ってはいけない表現]
- [責任転嫁につながる言い回し禁止]
```

### 運用/トラブル系（カテゴリ11）

```markdown
# 対象システム
[システム名・バージョン]

# 文書種別
[手順書 / Runbook / ポストモーテム / 障害切り分けフロー]

# 読み手
[ジュニアSE / 経験豊富な運用担当 / オンコール]

# 構成
- 手順番号必須
- 想定エラーと対処を併記
- ロールバック手順を必須化
- 再発防止案を含む（ポストモーテムの場合）
```

### リバースエンジニアリング系（カテゴリ12）

```markdown
# 入力種別
[ソースコード / API応答 / DBダンプ / ログ / バイナリ]

# 入力アクセス方法
- Claude Code向け: @[ファイルパス] を Read で読み込む
- 他AI向け: 以下に貼り付け

# 復元レベル
[詳細設計 / 基本設計 / 要件 / アルゴリズム]

# 出力フォーマット
[シーケンス図(Mermaid) / ER図 / 処理フロー / 仕様書 / 疑似コード]

# 確度表記の強制【重要】
各仕様項目には以下のタグを必ず付与すること：
- [確定] コード/挙動から明確に確認できる
- [推測] 合理的に推測される（理由を併記）
- [要確認] 不明・矛盾がある（理由を併記）

不明な点を「たぶん〇〇です」と確定的に書くことは厳禁。
「不明」と書く方が価値があります。

# 対象技術
- 言語/プラットフォーム: [COBOL / VB6 / Java 8 / 旧FW 等]
- 既存資料: [部分的にあり / 全くなし]
```

### DB/SQL系（カテゴリ13）

```markdown
# DBエンジン
- 種類: [PostgreSQL / MySQL / Oracle / SQL Server / BigQuery / Snowflake 等]
- バージョン: [15 / 8.0 / 19c / 2019 等]

# テーブル定義
[DDL / 構造説明 / @ファイルパス指定]

# 用途
[クエリ生成 / 最適化 / DB設計 / 移行 / リバース]

# データ特性
- 行数概算: [〇〇万行]
- インデックス: [既存インデックスの情報]
- データ分布: [偏りの有無]

# 安全装置（破壊系SQL含む場合は必須）
- WHERE句の対象範囲を必ずSELECTで先に確認する手順を提示
- トランザクションで囲むこと（BEGIN; ... ROLLBACK; で動作確認、最後にCOMMIT）
- バックアップ取得の推奨を明記
- 影響行数の想定を明示
```

### その他/自由（カテゴリ15）

```markdown
# 自由形式
ユーザーの説明に基づきLayer 1のみ必須、その他は柔軟に追加。
```

```markdown
- [URL / ファイルパス / 書籍名]
```

## 出力時の最終整形ルール

### Markdown標準フォーマット（デフォルト）

````markdown
```text
# 役割
[内容]

# 背景・前提
[内容]

# タスク
[内容]

# 出力形式
[内容]

# [カテゴリ別Layer 2要素]
[内容]

# [Layer 3要素 - 必要なら]
[内容]
```
````

### プレーンテキスト版（要求時）

Markdownマークアップ（# など）を外し、見出しは「【】」で囲む。

```
【役割】
[内容]

【背景・前提】
[内容]
...
```

### 英語版（要求時）

すべての見出しを英語化：

```text
# Role
# Context
# Task
# Output Format
# Constraints
# Examples
```

### バイリンガル版（要求時）

各見出しを日英併記：

```text
# 役割 / Role
[日本語]
[English]

# 背景 / Context
[日本語]
[English]
```

## 提示時の解説テンプレート

プロンプト本体の後に必ず添える。

```markdown
【プロンプトの意図】
- 役割を「[〇〇]」にした理由: [〇〇]
- 背景に「[〇〇]」を含めた理由: [〇〇]
- 出力形式を「[〇〇]」にした理由: [〇〇]
- [カテゴリ別の特殊指示があれば、その理由]

【使い方のコツ】
- [シーン]では、追加で[〇〇]を伝えると精度が上がります
- [〇〇]の場合は、プロンプト内の[〇〇]部分を調整してください
- 想定される失敗パターン: [〇〇] → [調整方法]

💡 オプション:
  - 英語版が欲しい場合: 「英語版もください」
  - バイリンガル版（日英併記）が欲しい場合: 「バイリンガル版で」
  - プレーンテキスト版が欲しい場合: 「プレーン版で」
  - 定番化したい場合: 「定番化して」
```
