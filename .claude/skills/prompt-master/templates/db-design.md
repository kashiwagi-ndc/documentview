# 設計原則
- **データ整合性 > 開発容易性 > 性能** の優先順位
- ただし「読み専用の集計テーブル」「履歴の非正規化」は実用上必要
- NULL を許容するかを明確に判断
- デフォルト値・制約は明示
- タイムスタンプは型と精度を統一（PostgreSQLなら TIMESTAMPTZ 推奨）

# DBエンジン固有の考慮
[エンジンに応じて]
- PostgreSQL: ENUM型 vs CHECK制約、JSONB、PARTIAL INDEX、CITEXT、GENERATED COLUMN
- MySQL: utf8mb4、InnoDB前提、生成列、JSON型の限界
- Oracle: シーケンス vs IDENTITY、NUMBER型の精度、VARCHAR2 vs CLOB
- BigQuery: パーティション・クラスタリング、ARRAY/STRUCT型

# 必須要素
- 各テーブルの「業務的意味」を明示
- インデックスには必ず「用途」を併記
- NULL許可/不許可を明示
- 主要な制約（UNIQUE / FK / CHECK）を網羅
- マイグレーション順序を考慮（FK依存）

# やってはいけないこと
- 命名の不統一
- 主キーの型不統一（一部 BIGINT、一部 UUID 等）
- 過剰な正規化（パフォーマンス無視の理論優先）
- 安易な非正規化（理由なしで JSON 詰め込み等）
- 暗黙的なNULL（NOT NULL or DEFAULT を必ず判断）
- インデックスの過剰追加（更新性能を犠牲にしない）

## 使い方のコツ
- **業務ルールを箇条書きで列挙**することで、AIが必要な制約・関連を導出できる
- 想定クエリパターンを伝えると、インデックス設計が最適化される
- 既存スキーマとの連携がある場合、命名規則を統一指示することで一貫性が保たれる
- DDL出力に「コメント（COMMENT ON COLUMN）」を含める指示を入れると、後の保守性が上がる

## 想定される失敗パターン
- **命名の不統一** → 命名規則を最初に明示
- **NULLの曖昧化** → 「NOT NULL or DEFAULT を必ず判断」を必須化
- **インデックス過剰** → 「インデックスに用途を併記」を必須化
- **業務ルールの欠落** → ビジネスルールを箇条書きで明示
