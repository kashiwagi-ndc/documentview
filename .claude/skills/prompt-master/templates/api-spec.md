# Template: API仕様書

## 用途
REST API / GraphQL API / WebSocket API などの仕様書をAIに生成させるプロンプトを生成する。新規API設計時、または既存APIの仕様書化に使う。

## カテゴリ
設計書/ドキュメント系（7）

## 短縮ヒアリング（4問）
1. **API種別**は？（REST / GraphQL / WebSocket / gRPC）
2. **API用途**は？（社内連携 / 顧客向け公開API / モバイルアプリBE / B2B連携）
3. **既存リソース・エンドポイント**情報の有無は？（@ファイルパス / 概要のみ / ゼロから）
4. **読み手**は？（自社開発者 / 顧客の開発チーム / 外部パートナー）

## プロンプト本体テンプレ

```text
# 役割
あなたはAPI設計に精通したシニアバックエンドエンジニアです。
RESTful原則・OpenAPI仕様・セキュリティベストプラクティスに従い、
読み手が実装に迷わない明確な仕様書を作成するプロフェッショナルです。

# 背景・前提
- API種別: [REST / GraphQL / WebSocket / gRPC]
- API用途: [社内連携 / 公開API / モバイルアプリBE / B2B連携]
- 提供するリソース: [リソース名一覧]
- 認証方式: [API Key / Bearer Token / OAuth 2.0 / mTLS]
- ベースURL: [https://api.example.com/v1]
- バージョニング戦略: [URLパス / ヘッダ / クエリ]
- レート制限: [あり / なし]

# 読み手
- 対象: [自社開発者 / 顧客の開発チーム / 外部パートナー]
- 技術レベル: [中級 / 上級]
- 既存API利用経験: [あり / なし]

# 入力素材
[ゼロから設計の場合]
要件のみ記載

[既存APIの仕様書化の場合]
@[ソースコードパス] を Read で読み込んで、エンドポイント・パラメータを抽出してください

# タスク
[新規設計 / 既存仕様書化]のAPI仕様書を作成してください。
読み手が実装で迷わない、エラーパターンまで網羅した仕様書にしてください。

# 出力形式
- 形式: Markdown（OpenAPI 3.0 YAMLも併記可）
- 構成:
  1. 📋 概要
     - API名・目的
     - ベースURL・バージョン
     - 認証方式
     - レート制限
  2. 🔐 認証
     - 認証フロー
     - トークン取得方法
     - 有効期限・更新方法
  3. 📊 共通仕様
     - リクエストヘッダ
     - レスポンス形式（JSON構造）
     - エラーレスポンス形式
     - HTTPステータスコード方針
     - 日付・タイムスタンプ形式
     - ページネーション方式
  4. 🔌 エンドポイント一覧
     - メソッド・パス・概要の一覧表
  5. 📝 エンドポイント詳細（各エンドポイントごと）
     - メソッド + パス
     - 説明
     - リクエストパラメータ（パス / クエリ / ボディ）
     - リクエスト例（cURL / JSON）
     - レスポンス例（成功 / 各エラー）
     - エラーパターン一覧
     - 必要な権限
     - レート制限の特例
  6. ❌ エラーコード一覧
     - エラーコード / メッセージ / 対処方法
  7. 🔄 変更履歴
- トーン: 技術文書・正確・簡潔

# 必須要素
- 全エンドポイントに「リクエスト例」「成功レスポンス例」「主要エラー例」を含める
- エラーコードは必ず一覧化（横断検索可能に）
- 認証フローは図解（Mermaid）も含める
- 「冪等性の有無」を明示
- バージョニング戦略を明記

# やってはいけないこと
- パラメータの型を曖昧にする（string / number / boolean等を明示）
- 必須/任意パラメータの区別を省く
- エラーレスポンスを「適切なエラー」とぼかす
- 認証エラーと認可エラーを混同する
- レスポンス例を1パターンしか書かない（成功例だけで終わらせない）
```

## 使い方のコツ
- **OpenAPI 3.0 YAML併記を指定**するとそのままSwagger UIに読ませられるので便利
- **既存仕様書化の場合は `@src/routes/*.ts` 等で Read 指定**するとコードから直接抽出できる
- 公開APIの場合は「セキュリティ考慮事項」セクションを追加で要求するとなお良い
- B2B連携の場合は「リトライ方針」「タイムアウト推奨値」も追加すべき

## 想定される失敗パターン
- **エラーパターンの記述漏れ** → 「主要エラー例」を必須化
- **型情報の曖昧化** → 「型を明示」を強化
- **認証セクションが薄い** → 「認証フロー図解」を必須化
- **冪等性の不明確化** → 必須要素に追加
