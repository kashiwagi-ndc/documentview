# Template: 技術選定比較

## 用途
プログラミング言語・フレームワーク・ライブラリ・ミドルウェア・クラウドサービス等の技術選定で、複数候補を体系的に比較するプロンプトを生成する。

## カテゴリ
リサーチ/競合調査系（6）

## 短縮ヒアリング（4問）
1. **比較対象**は？（例：Next.js vs Remix vs Nuxt / Datadog vs NewRelic vs Grafana）
2. **使用シーン・要件**は？（規模・性能・チームスキル・予算 等）
3. **比較軸**の優先順位は？（性能 / 学習コスト / コミュニティ / 採用実績）
4. **意思決定者**は？（自分 / チーム / 経営層）

## プロンプト本体テンプレ

```text
# 役割
あなたはフルスタック経験豊富なテックリードです。
技術選定では「現時点のトレンド」だけでなく、3〜5年後の保守性・スケーラビリティまで見据えた判断を下すプロフェッショナルです。
各技術の強み・弱み・トレードオフを客観的に評価します。

# 背景・前提
- 比較対象: [技術A / 技術B / 技術C]
- プロジェクト性質: [新規開発 / リプレース / マイクロサービス追加]
- 規模: [小規模/中規模/大規模 + 想定ユーザー数・データ量]
- チーム構成: [メンバー数 / スキルセット / 経験年数]
- 既存技術スタック: [既存システムとの連携要件]
- 時間軸: [短期PoC / 中期本番 / 長期保守]

# 比較軸（優先順位順）
1. [軸1 — 例：パフォーマンス]
2. [軸2 — 例：学習コスト]
3. [軸3 — 例：コミュニティ・エコシステム]
4. [軸4 — 例：保守性・更新頻度]
5. [軸5 — 例：採用実績・将来性]
6. [軸6 — 例：エコシステム連携]

# 制約・前提条件
- 予算: [指定があれば]
- 既存資産: [既存スキル / 既存システム]
- コンプライアンス: [ライセンス制約 / GPL不可 等]
- 採用しない理由が明確な候補: [〇〇は除外（理由）]

# 意思決定者
- 役職: [技術選定責任者 / CTO / 経営層]
- 重視するポイント: [技術力 / コスト / リスク / スピード]

# 出典の扱い
- 公式ドキュメント・GitHub Issues・公式ベンチマークを優先参照
- 各項目に出典URLを明記
- 「自分の体感」「コミュニティの噂」は明示してそれと分かるように
- 不確実な情報は「[要確認]」とマーク

# タスク
上記の技術を上記の比較軸で詳細比較し、本プロジェクトへの推奨を結論として提示してください。

# 出力形式
- 形式: Markdown
- 構成:
  1. 📋 サマリー（推奨技術と理由3点）
  2. 📊 比較表（縦：軸、横：技術 + スコア or 評価）
  3. 🔍 各技術の詳細評価
     - 強み（具体例つき）
     - 弱み（具体例つき）
     - 採用実績（有名企業・OSS事例）
     - エコシステム（周辺ツール・ライブラリ）
     - 将来性（直近のリリース傾向・コミット数推移）
     - 学習コスト
     - 想定される落とし穴
  4. 🎯 推奨と採用根拠
     - 第一推奨と理由
     - 次点候補と理由
     - 採用すべきでない選択肢と理由
  5. ⚠️ 採用後のリスクと対策
     - 技術リスク
     - 移行リスク（既存からの場合）
     - チームスキルギャップ
  6. 💰 コスト試算（ライセンス・運用・学習コスト）
  7. 📚 出典リスト

# 必須要素
- 推奨技術には必ず「採用根拠」3点以上
- 採用しない選択肢にも明確な理由
- 既存技術スタックとの相性を明示
- チームのスキルセットを考慮した推奨
- 3〜5年後の保守性に言及

# やってはいけないこと
- トレンドだけで判断する（古い枯れた技術にも長所あり）
- 自分の好み・推し技術を理由なく推す
- 全部の技術を平等に褒める（結論を曖昧にしない）
- ベンチマーク数値の出典なし主張
```

## 使い方のコツ
- **意思決定者の重視ポイント**を聞くと結論の見せ方が変わる：
  - 経営層 → コストとリスク中心
  - CTO → 戦略的整合性
  - 現場リード → 実装・運用の現実
- 「採用しない選択肢の理由」を明示することで、後から「なぜAじゃなくてBにした？」と聞かれた時の防御線になる
- 3〜5年後を見据えた評価を入れると、「流行っているから採用」の罠を避けられる

## 想定される失敗パターン
- **トレンドだけで判断** → 「3〜5年後の保守性に言及」を必須化
- **結論が曖昧** → 「推奨と採用根拠を3点以上」を強化
- **既存資産の無視** → 「既存技術スタックとの相性」を必須化
- **チームスキルの無視** → 「チームスキルセットを考慮」を強化
