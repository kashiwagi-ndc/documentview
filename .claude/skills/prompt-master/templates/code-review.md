# Template: コードレビュー依頼

## 用途
既存のコードをAIにレビューしてもらうためのプロンプトを生成する。バグ検出・設計改善・規約準拠・性能観点等の指摘を引き出す。

## カテゴリ
コード/技術系（2）

## 短縮ヒアリング（4問）
1. **言語・FW・バージョン**は？（例：TypeScript / React 18 / Node 20）
2. **レビュー観点**の優先順位は？（バグ / 設計 / 性能 / セキュリティ / 可読性）
3. **コードへのアクセス方法**は？（@ファイルパス / コピペ）
4. **コーディング規約**はありますか？（社内規約 / ESLint設定 / 一般的）

## プロンプト本体テンプレ

```text
# 役割
あなたは[言語・FW]に精通したシニアエンジニアです。
コードレビューでは、表層的な指摘ではなく「なぜそれが問題か」を論理的に説明し、
具体的な改善案まで提示することを徹底します。

# 背景・前提
- 言語: [言語とバージョン]
- フレームワーク/ライブラリ: [名称とバージョン]
- ランタイム: [Node 20 / Python 3.12 等]
- プロジェクト性質: [新規 / 既存改修 / レガシー保守]
- コードベース規模: [単一ファイル / モジュール / プロジェクト全体]
- コーディング規約: [社内規約 / ESLint Recommended / Airbnb / 一般的なベストプラクティス]

# レビュー観点（優先順位順）
1. [バグ / 不具合の可能性]
2. [設計・アーキテクチャ]
3. [性能・スケーラビリティ]
4. [セキュリティ]
5. [可読性・保守性]
6. [テスト容易性]

# コードへのアクセス
[Claude Code向け] @[ファイルパス] を Read で読み込んでレビュー
[他AI向け] 以下のコードをレビュー: [コード貼り付け]

# タスク
上記のコードを上記観点で詳細にレビューし、改善提案を提示してください。

# 出力形式
- 形式: Markdown
- 構成:
  1. 📋 サマリー（全体評価3〜5行）
  2. 🔴 重大な指摘（バグ / セキュリティリスク 等）
  3. 🟡 改善推奨（設計 / 性能 / 可読性）
  4. 🟢 良い点・維持すべきポイント
  5. 📝 各指摘の詳細（番号付き）
     - 該当箇所: ファイル名:行番号
     - 問題: なぜそれが問題か
     - 影響: 放置するとどうなるか
     - 改善案: 具体的な修正コードまたは方針
     - 優先度: 必須 / 推奨 / 任意

# 指摘のタグ付け
各指摘に以下のタグを付与すること:
- [BUG] 動作不良につながる
- [SEC] セキュリティリスク
- [PERF] 性能影響
- [DESIGN] 設計改善
- [READ] 可読性
- [TEST] テスト容易性
- [STYLE] スタイル・命名

# やってはいけないこと
- 「リファクタリングしたほうがいい」等の根拠不明な指摘
- 全部書き直しを提案するような大規模変更（小さく改善できる箇所を優先）
- 主観的な好み（「個人的にはこう書く」等）
- 規約準拠の指摘で具体的な規約名を出さない

# 補足
- 明らかな問題がない場合は「重大な指摘なし」と明記してください
- 不明な点（前後のコンテキストが見えない等）は推測せず「[要確認]」とマーク
```

## 使い方のコツ
- **Claude Code環境では `@path/to/file.ts` 指定が圧倒的に効率的** — 大量コードをコピペする必要がない
- レビュー観点の優先順位を明示すると、AIが何を重点的に見るかブレない
- コーディング規約を「Airbnb」「ESLint Recommended」等の具体的な名称で指定すると、ルール違反の指摘が正確になる

## 想定される失敗パターン
- **指摘が浅い・抽象的** → 「該当箇所: ファイル名:行番号」を必須化
- **全部書き直し提案になる** → 「小さく改善できる箇所を優先」を強化
- **規約違反指摘の根拠が弱い** → 「具体的な規約名を出す」を必須化
