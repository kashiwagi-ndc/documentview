# Template: API挙動 → 仕様書

## 用途
ドキュメントがないAPIの実際の挙動（リクエスト・レスポンス例 / ソースコード）から仕様書を復元するプロンプトを生成する。サードパーティAPI連携・社内API引き継ぎで活用。

## カテゴリ
リバースエンジニアリング系（12）

## 短縮ヒアリング（4問）
1. **API種別**は？（REST / GraphQL / SOAP / 独自プロトコル）
2. **入力素材**は？（ソースコード / Postmanコレクション / 実際のHTTPログ / 挙動の説明）
3. **既知のエンドポイント数**は？（数個 / 10〜30 / 30以上）
4. **欲しい出力**は？（Markdown仕様書 / OpenAPI YAML / 両方）

## プロンプト本体テンプレ

```text
# 役割
あなたはAPI解析とOpenAPI仕様策定に精通したシニアエンジニアです。
ドキュメントのないAPIから、実際の挙動・ソースコード・通信ログを総合して正確な仕様書を復元するプロフェッショナルです。

# 背景・前提
- API種別: [REST / GraphQL / SOAP / 独自]
- 解析対象システム: [システム名・提供元]
- 既存資料: [部分的にあり / Postmanコレクションのみ / 全くなし]
- 解析の目的: [連携実装 / 引き継ぎ / 移行 / 監査]

# 入力アクセス
[Claude Code向け]
@[ソースコード / Postmanファイル / HTTPログ] を Read で読み込んでください

[他AI向け]
以下の入力素材を解析してください:
[コード / Postmanコレクション / リクエスト・レスポンス例 貼り付け]

# 解析対象
- 対象エンドポイント: [全部 / 特定機能領域]
- 認証方式: [既知の認証方式があれば]

# タスク
入力素材からAPI仕様書を復元してください。
実際の挙動から明確に分かる部分と、推測の部分を厳密に区別してください。

# 出力形式
- 形式: Markdown（OpenAPI 3.0 YAML併記可）
- 構成:
  1. 📋 概要
     - API全体の目的（推定）
     - ベースURL（確認できる範囲）
     - 認証方式（推定 or 確認）
  2. 🔌 エンドポイント一覧
     - メソッド / パス / 推定される目的 / 確度タグ
  3. 📝 エンドポイント詳細（各エンドポイントごと）
     - メソッド + パス
     - 説明（業務的意味の推定）
     - リクエスト
       - パスパラメータ
       - クエリパラメータ
       - ヘッダ
       - ボディ（型・必須/任意・意味の推定）
     - レスポンス
       - 成功レスポンス（実例ベース）
       - エラーレスポンス（観測できたパターン）
     - 実例
     - 確度タグ
  4. 🔐 認証フロー（観測できる範囲で）
  5. ❌ エラーパターン
     - 観測できたエラーコード一覧
     - 推定される他のエラー（未観測だが存在しそうなもの）
  6. 🔍 共通仕様の推定
     - 日付フォーマット
     - ページネーション方式
     - ID体系（UUID / 連番 / 等）
     - 命名規則
  7. ❓ 不明点・推測が多い箇所
     - パラメータの意味不明（特にフラグ系・コード系）
     - エラーパターンの網羅性不明
     - レート制限・タイムアウト等の運用ルール不明
  8. 📋 検証推奨事項
     - 不明点を確認するための検証方法（実APIを叩く / ログを観察する 等）

# 確度表記の強制【最重要】
各項目に以下のタグを必ず付与:
- [確定] 実例・コード・公式情報から明確
- [推測] 命名・他エンドポイントとの一貫性から推測（理由併記）
- [要確認] 不明・実際の挙動を検証する必要あり

# やってはいけないこと
- 観測されていない挙動を「[確定]」として扱う
- レート制限・タイムアウトを推測で断定
- 認証エラーと認可エラーを混同
- リクエストパラメータの必須/任意を一観測例から断定（複数例の比較が必要）
- 実装の挙動を「正しい仕様」として書く（バグの可能性を考慮）

# 補足の指示
- 同じエンドポイントで複数のレスポンスパターンが観測されている場合は、すべてのパターンを記述
- パラメータの組み合わせで挙動が変わる場合、その条件を整理
- 「実装はこうなっているが、正しい仕様かは別途確認すべき」事項を明記
```

## 使い方のコツ
- **Postmanコレクションがある場合は最強の入力素材** — リクエスト・レスポンス例が揃っている
- **HTTPログ（DevToolsエクスポート等）も有用** — 実挙動を最も正確に反映
- 「実装の挙動 = 正しい仕様」とは限らないので、検証推奨事項を必ず出させる
- 推測の多いセクションは、後でクライアント実装する時のテストケース候補にもなる

## 想定される失敗パターン
- **未観測挙動の断定** → 「観測例ベースで」を強調
- **パラメータの必須/任意の誤推定** → 「複数例の比較が必要」を明示
- **エラーパターンの過剰補完** → 「観測できたエラー」と「推定」を分離
- **認証フローの推測** → 認証関連は[要確認]を多用させる
