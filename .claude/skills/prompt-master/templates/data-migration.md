# 安全装置（必須）
- すべての破壊系SQL（DELETE/UPDATE/TRUNCATE）は：
  - WHERE句の対象範囲を必ずSELECTで先に確認
  - トランザクションで囲む（BEGIN; ... ROLLBACK; で動作確認、COMMIT）
  - バックアップ前提
  - 影響行数の想定を明示
- 段階的実行を推奨（一括ではなく機能領域単位）
- 各ステップで件数・サンプル確認

# 必須要素
- バックアップ・切戻し手順を必ず含める
- 各ステップに「進む/戻る」の判断基準を明示
- 整合性検証SQLを充実させる（移行漏れの早期発見）
- 性能観点（バッチサイズ・コミット粒度）を考慮
- データ型変換時のエッジケース（NULL / 空文字 / 桁あふれ）を明示

# やってはいけないこと
- バックアップなしの移行
- WHERE句なしの DELETE / UPDATE
- 一括コミット（巨大トランザクション）
- 整合性検証を省く
- 切戻し手順を考えない
- 性能影響を測定せずに本番実行

## 使い方のコツ
- **段階的実行を強く推奨** — 一括で失敗すると切戻しが大変
- 並行稼働期間を設ける場合、差分検出ロジックも併せて設計する
- 大規模データ（1億行以上）は、バッチサイズ・並列度を別途調整
- 移行先環境での「事後確認SQL」を充実させると、ビジネス側の検証も容易

## 想定される失敗パターン
- **バックアップなしで実行** → 「バックアップ・切戻し手順を必須化」
- **巨大トランザクション** → 「バッチサイズ・コミット粒度を考慮」を強化
- **整合性検証漏れ** → 「整合性検証SQL」を必須セクション化
- **データ型変換のエッジケース** → 「NULL / 空文字 / 桁あふれを明示」を必須化
