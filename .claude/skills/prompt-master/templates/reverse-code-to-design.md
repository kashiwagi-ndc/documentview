# Template: コード → 基本設計書ドラフト

## 用途
仕様書のない既存システムからコードベース全体を解析し、基本設計書（または引き継ぎ用ドキュメント）のドラフトを作成するプロンプトを生成する。レガシーシステム引き継ぎの最終アウトプット。

## カテゴリ
リバースエンジニアリング系（12）／設計書/ドキュメント系（7）

## 短縮ヒアリング（4問）
1. **対象システム**は？（システム名・想定される業務領域）
2. **対象範囲**は？（システム全体 / 特定機能 / 特定モジュール）
3. **入力**は？（@ディレクトリパス指定 / 個別ファイル列挙）
4. **設計書のフォーマット**は？（一般的 / 社内テンプレあり / 簡易引き継ぎメモ）

## プロンプト本体テンプレ

```text
# 役割
あなたはSIプロジェクトのリバースエンジニアリングに精通したシニアシステムアーキテクトです。
コードベース全体から業務ロジック・データフロー・システム構成を抽出し、後任者が運用・改修できる設計書を作成するプロフェッショナルです。
推測と確定を厳密に区別し、不明な点は必ず明示します。

# 背景・前提
- 対象システム: [システム名]
- 想定される業務領域: [販売管理 / 在庫管理 / 顧客管理 等]
- 言語/プラットフォーム: [Java + Spring Boot / VB.NET / COBOL 等]
- アーキテクチャ推定: [モノリス / レイヤード / マイクロサービス 等]
- コードベース規模: [ファイル数 / LOC]
- 既存資料: [部分的にあり / コメントのみ / 全くなし]
- 解析の目的: [引き継ぎ / 改修前理解 / 移行検討 / 監査]

# 入力アクセス
[Claude Code向け]
@[プロジェクトルートディレクトリ] を Read 含めて段階的に解析してください

[他AI向け]
入力規模が大きいため、以下の方針で進めてください:
1. まず全体構造の把握（ディレクトリ構成・主要モジュール）
2. エントリポイントの特定
3. 主要処理フローの解析
4. 段階的に詳細を追加

# 対象範囲
- システム全体 / [特定機能領域: 〇〇]

# タスク
コードベースから基本設計書ドラフトを作成してください。
完全な設計書である必要はなく、「後任者がコードを読まなくても全体像を把握でき、必要時に該当箇所を探せる」ことを目標とします。

# 出力形式
- 形式: Markdown
- 構成:
  1. 📋 システム概要
     - システム名と目的（推定含む）
     - 主要な業務機能
     - 利用者・ステークホルダー（推定）
     - 確度タグ
  2. 🏗️ システム構成
     - アーキテクチャ全体図（Mermaid）
     - 主要コンポーネントと役割
     - 外部システム連携
     - 採用技術スタック（言語/FW/DB/インフラ）
  3. 📂 ディレクトリ構成と責務
     - 主要ディレクトリの一覧と役割
     - パッケージ構成のパターン
  4. 🔌 主要機能一覧
     - 機能ID（仮）/ 機能名 / 概要 / 関連ファイル / 確度タグ
  5. 📊 データ構造
     - 主要エンティティ一覧（DB / メモリ）
     - データフロー概要
     - 外部I/O（API / ファイル / メッセージ）
  6. 🔄 主要処理フロー（代表的なユースケース 3〜5件）
     - ユースケース名
     - 関連ファイル
     - 処理フローの概要（テキスト or Mermaid）
  7. 🛡️ 横断的関心事
     - 認証・認可
     - ロギング
     - エラーハンドリング
     - トランザクション管理
     - 性能・キャッシュ
  8. 🚀 運用関連
     - ビルド方法
     - デプロイ方法
     - 主要設定ファイル
     - 環境変数
  9. ⚠️ 注意事項・技術的負債
     - 古いライブラリ・非推奨機能の使用
     - 性能ボトルネック疑い
     - セキュリティ懸念
     - 命名・構造の不統一
  10. ❓ 不明点リスト（最重要）
      - コードからは判断できない業務ルール
      - 元仕様書・元開発者への確認事項
      - 推測の根拠が弱い箇所
  11. 📚 解析の制約事項
      - 解析できなかった範囲
      - 解析の前提条件
      - 確度の高い情報源 vs 推測情報源

# 確度表記の強制【最重要】
各セクションの主要記述に以下のタグを付与:
- [確定] コードから明確に確認できる
- [推測] 命名・構造・パターンから推測（理由併記）
- [要確認] 不明・矛盾あり（理由併記）

# 段階的解析の方針
入力が大規模な場合、以下の順で進めてください:

段階1: 構造把握
  - ディレクトリ構成 / 主要モジュール / 採用技術
  - エントリポイント（main / API route / Controllerなど）

段階2: 動作仕様
  - 主要機能のリスト化
  - 各機能のエントリポイントから処理フロー
  - DBスキーマ・外部I/O

段階3: 業務仕様
  - ビジネスルールの抽出
  - 複雑な処理の業務的意味推定
  - エッジケース・例外処理

段階4: 設計書化
  - 上記をフォーマットに沿って整理
  - 図表（Mermaid）の作成
  - 不明点リストの作成

# やってはいけないこと
- 推測の業務ルールを断定的に記述
- 命名から業務エンティティを断定
- バグや非推奨実装を「正しい仕様」として書く
- 解析できなかった範囲を明示しない
- 完璧を目指して時間切れになる（不完全でも全体像優先）
```

## 使い方のコツ
- **規模が大きい場合は段階的に**：いきなり全部を求めず、段階1（構造把握）→ 段階2（動作仕様）と分割
- **Claude Code環境では `@プロジェクトルート/` 指定で段階的に Read** させると効率的
- 「不明点リスト」が最も価値が高い。ここが充実していれば、元開発者への確認が効率化できる
- 「解析の制約事項」を明示することで、後任者が「どこまで信用していいか」が分かる

## 想定される失敗パターン
- **業務ルールの過剰推測** → 「業務ルールは[推測]タグ必須」を強化
- **技術的負債を肯定的に記述** → 「注意事項・技術的負債」セクションを必須化
- **不明点が抜ける** → 「不明点リスト」を最重要セクションとして強調
- **時間切れで一部のみ** → 段階的解析を明示的に推奨
