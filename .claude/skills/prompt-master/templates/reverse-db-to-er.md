# Template: DB → ER図 / テーブル定義書

## 用途
既存DBのDDL・スキーマダンプから、ER図とテーブル定義書を復元するプロンプトを生成する。レガシーDB引き継ぎ・移行案件で活躍。

## カテゴリ
リバースエンジニアリング系（12）／DB/SQL系（13）

## 短縮ヒアリング（4問）
1. **DBエンジン**は？（PostgreSQL / MySQL / Oracle / SQL Server / 等）
2. **入力**は？（DDL / スキーマダンプ / 実DB接続情報 / @ファイルパス）
3. **テーブル数**の規模は？（10未満 / 10〜50 / 50以上）
4. **欲しい出力**は？（ER図のみ / テーブル定義書のみ / 両方）

## プロンプト本体テンプレ

```text
# 役割
あなたはDB設計とデータ移行に精通したシニアDBA兼データアーキテクトです。
既存スキーマから業務エンティティと関連を正確に復元し、推測と確定を厳密に区別するプロフェッショナルです。

# 背景・前提
- DBエンジン: [PostgreSQL 15 / MySQL 8.0 / Oracle 19c / SQL Server 2019 等]
- スキーマ規模: [テーブル数 約N個]
- 既存資料: [部分的にあり / 全くなし / コメントなし]
- 命名規則: [snake_case / camelCase / 日本語ローマ字 等]
- 解析の目的: [引き継ぎ / 移行 / 機能改修 / 障害調査]

# 入力アクセス
[Claude Code向け]
@[DDLファイル / スキーマダンプファイル] を Read で読み込んでください

[他AI向け]
以下のDDLを解析してください:
[DDL貼り付け]

# 解析対象
- 対象テーブル: [全テーブル / 特定スキーマ / 特定機能領域]
- 除外: [履歴テーブル / 一時テーブル等の除外指定があれば]

# タスク
スキーマからER図とテーブル定義書を復元してください。
命名規則・カラム名・型情報・制約から業務エンティティを推定し、確度を明示してください。

# 出力形式
- 形式: Markdown + Mermaid ER図
- 構成:
  1. 📋 概要
     - 業務ドメインの推定（1〜2文）
     - 主要エンティティの数と分類（マスタ / トランザクション / 履歴）
  2. 🔗 ER図（Mermaid）
     ```mermaid
     erDiagram
       USERS ||--o{ ORDERS : places
       ORDERS ||--|{ ORDER_ITEMS : contains
       PRODUCTS ||--o{ ORDER_ITEMS : referenced
       USERS {
         bigint id PK
         varchar email UK
         varchar name
         timestamp created_at
       }
       ORDERS {
         bigint id PK
         bigint user_id FK
         decimal total
         varchar status
       }
     ```
  3. 📊 テーブル定義書（各テーブルごと）
     - テーブル名 + 業務的意味（推定含む）
     - カラム一覧（列名 / 型 / NULL許可 / デフォルト / 制約 / 業務的意味 / 確度タグ）
     - 主キー
     - 外部キー
     - インデックス
     - 想定される業務ルール
  4. 🔍 命名規則の解釈
     - prefix/suffix のパターン
     - 略語の解釈
     - 「分かったこと」と「不明な命名」
  5. 🧩 推定される業務エンティティの関連
     - マスタテーブル
     - トランザクションテーブル
     - 中間テーブル（多対多）
     - 履歴・監査テーブル
  6. ⚠️ 設計上の懸念
     - 正規化レベル
     - 性能ボトルネックになりそうな箇所
     - 不適切な型選択の疑い
     - 命名の不統一
  7. ❓ 不明点（要確認リスト）
     - カラムの意味が不明（特にフラグ系・コード系）
     - 関連が不明（暗黙的な外部キー）
     - 業務ルールが推測の域を出ない事項

# 確度表記の強制【最重要】
各カラムの「業務的意味」には以下のタグを付与:
- [確定] カラム名・型・制約・既存資料から明確
- [推測] 命名規則・他テーブルの関連から推測（理由併記）
- [要確認] 不明・矛盾あり（理由併記）

例:
- `user_id` → ユーザーID（USERSテーブルへの外部キー） [確定]
- `del_flg` → 論理削除フラグ [推測：命名から削除フラグと推定]
- `kbn1` → 区分1 [要確認：何の区分か不明、定数マスタが必要]

# やってはいけないこと
- 暗黙的な外部キー関係を「[確定]」として扱う（型の一致だけで断定しない）
- 「del_flg=1 なら削除」等のフラグ値の意味を推測のまま断定
- カラム名から業務ルールを過剰推測する
- インデックスから「これは検索によく使われる」と断定（推測なら[推測]タグ）
```

## 使い方のコツ
- **DDLファイル全体を `@schema.sql` で読ませる**のが効率的
- 規模が大きい場合（50テーブル以上）は機能領域ごとに分けて実行
- 命名規則が日本語ローマ字の場合、その旨を明示すると解釈精度が上がる
- 「マスタ / トランザクション / 履歴」の分類を求めると、業務理解が早い

## 想定される失敗パターン
- **暗黙的FKの誤検出** → 「型一致だけで断定しない」を強化
- **フラグ値の意味推測** → 「フラグ値は[要確認]」を必須化
- **大規模スキーマで漏れ** → 機能領域分割を推奨
- **コードマスタ依存項目の処理** → 「コードマスタが必要」と明示させる
