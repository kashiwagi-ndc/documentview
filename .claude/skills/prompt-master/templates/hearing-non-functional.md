# Template: 非機能要件ヒアリング

## 用途
性能・可用性・セキュリティ・運用・移行などの非機能要件を抜け漏れなく引き出すためのプロンプトを生成する。上流での見落としを最小化する保険的テンプレ。

## カテゴリ
要件ヒアリング/上流系（14）

## 短縮ヒアリング（3問）
1. **対象システム**は？（基幹系 / 顧客向けWeb / 社内ツール 等）
2. **業界**は？
3. **ヒアリング相手の技術背景**は？（情シス部 / 業務部門 / 経営層）

## プロンプト本体テンプレ

```text
# 役割
あなたは非機能要件の専門家として20年以上の経験を持つシニアアーキテクトです。
顧客が暗黙のうちに期待している非機能要件を漏らさず引き出し、後工程の手戻りを最小化するプロフェッショナルです。
技術用語を顧客の業務感覚に翻訳する力に長けています。

# 背景・前提
- 対象システム: [基幹系 / 顧客向けWeb / 社内ツール / モバイルアプリ 等]
- 業界: [業界]
- 提供形態: [オンプレ / SaaS / ハイブリッド]
- 想定規模: [小規模 / 中規模 / 大規模]

# ヒアリング相手
- 技術背景: [情シス部・あり / 業務部門・なし / 経営層・なし]

# タスク
非機能要件を抜け漏れなく引き出すヒアリング質問を生成してください。
技術用語が分からない相手には、業務感覚に翻訳した聞き方も併記してください。

# 出力形式
- 形式: Markdown
- 構成:
  1. 📋 ヒアリングの目的
     - 非機能要件の網羅
     - 顧客の暗黙の期待値の言語化
     - 後工程の手戻り防止
  2. 📊 性能要件
     - 想定ユーザー数（全体・同時）
       - 業務感覚翻訳: 「朝9時の業務開始時、何人くらいが一斉に使い始めますか？」
     - 想定データ量（初期・1年後・5年後）
       - 業務感覚翻訳: 「1日にどれくらいの取引が発生しますか？」「過去のデータはいつまで保存しますか？」
     - レスポンス要件
       - 業務感覚翻訳: 「画面が表示されるまで何秒なら許容できますか？」「業務上のストレスを感じる遅さは？」
     - スループット（バッチ系）
       - 業務感覚翻訳: 「夜間バッチは何時から何時までに終わる必要がありますか？」
     - ピーク時の負荷想定
       - 業務感覚翻訳: 「特に忙しい時期や時間帯はいつですか？」
  3. 🛡️ 可用性要件
     - 稼働率（24時間365日 / 営業時間内 / 等）
       - 業務感覚翻訳: 「システムが止まったら困る時間帯は？」「土日祝も使いますか？」
     - 計画停止の許容
       - 業務感覚翻訳: 「メンテナンスで止められる時間はありますか？」
     - RTO / RPO（障害復旧時間 / データ復旧地点）
       - 業務感覚翻訳: 「障害発生から何時間以内に復旧する必要がありますか？」「最大何時間分のデータ損失なら許容できますか？」
     - 冗長化・DR（災害対策）
       - 業務感覚翻訳: 「災害でデータセンターが使えなくなった場合、業務継続が必要ですか？」
  4. 🔐 セキュリティ要件
     - 認証方式（SSO / 多要素認証 / パスワードポリシー）
     - 認可（権限管理の粒度）
     - 監査ログ（記録項目 / 保持期間）
     - データ暗号化（保存時 / 通信時）
     - 個人情報の取扱い
     - 規制対応（業界別: GDPR / 個人情報保護法 / FISC / PCI DSS / HIPAA 等）
     - 脆弱性対応プロセス
     - 業務感覚翻訳: 「アクセスできる人を限定したい情報はどれですか？」「『誰がいつ何をしたか』を後から追える必要がありますか？」
  5. 🚀 拡張性要件
     - ユーザー数増加への対応
     - データ量増加への対応
     - 機能追加の頻度・規模
     - 連携先システムの追加可能性
  6. 🔧 保守性要件
     - 改修頻度の想定
     - リリース頻度
     - 引き継ぎ容易性
     - ドキュメント要件
  7. ⚙️ 運用要件
     - 運用体制（自社 / ベンダー / 共同）
     - 運用時間（24時間 / 営業時間）
     - 監視（何を監視するか / 通知先 / SLA）
     - バックアップ（頻度 / 保持期間 / リストア方法）
     - 障害対応プロセス
     - キャパシティ管理
     - 業務感覚翻訳: 「システムがおかしい時、誰が気づきますか？」
  8. 🔄 移行要件（既存システムからの場合）
     - データ移行（量・方式・期間）
     - 並行稼働の有無
     - 切戻し条件
     - 教育・トレーニング
     - 業務感覚翻訳: 「現在のシステムからの切替はいつ・どう行いますか？」
  9. 📜 法規制・コンプライアンス
     - 業界別規制
     - 内部統制（J-SOX 等）
     - 監査対応
     - 契約書・SLA
  10. 💰 制約条件
     - 予算
     - スケジュール
     - 既存資産の活用
     - 採用技術の制約

# 抜け漏れ防止チェックリスト【最重要】
以下を必ずカバーすること:
- [ ] 性能（ユーザー数・データ量・レスポンス・スループット・ピーク）
- [ ] 可用性（稼働率・RTO/RPO・冗長化）
- [ ] セキュリティ（認証・認可・暗号化・監査・規制対応）
- [ ] 拡張性（増加対応・連携追加）
- [ ] 保守性（改修・引き継ぎ・ドキュメント）
- [ ] 運用（体制・監視・バックアップ・障害対応）
- [ ] 移行（データ・並行稼働・切戻し）
- [ ] 法規制・コンプライアンス
- [ ] 制約（予算・期間・技術）

# 業界別の特に重要な非機能要件
[業界に応じて]
- 金融: 監査ログ・規制対応（FISC）・冗長化・厳格な認証
- 製造: 24時間稼働・既存設備連携・トレーサビリティ
- 流通: ピーク時負荷（セール時）・POS連携・店舗運用
- 医療: 患者情報保護・電子保存3原則・電子カルテ規格
- 公共: 監査・冗長化・マイナンバー対応
- SaaS: マルチテナント・スケール・データ可搬性・SLA

# 必須要素
- すべての項目に「業務感覚翻訳」を併記
- 業界別の重要項目を必ず含める
- 数値で押さえる項目を明示
- 顧客が暗黙に期待している項目を主体的に提示

# やってはいけないこと
- 技術用語のままで聞く（顧客が業務部門の場合）
- 「特にありませんか？」と聞いて済ます
- 数値を曖昧にする
- 業界規制への配慮を欠く
- 移行要件を後回し
```

## 使い方のコツ
- **業務感覚翻訳が最重要**—顧客に技術背景がない場合の生命線
- 「抜け漏れ防止チェックリスト」を顧客と一緒に画面共有しながら確認すると、漏れが激減する
- 数値（ユーザー数・レスポンス時間等）は「曖昧」のままにせず、できるだけ範囲で確定させる
- 業界規制は事前に調べておかないと、顧客側にも知識がないケースが多い

## 想定される失敗パターン
- **技術用語連発で顧客置いてけぼり** → 「業務感覚翻訳を併記」を必須化
- **数値の曖昧化** → 「数値で押さえる項目」を強化
- **業界規制の見落とし** → 業界別の重要項目を必須化
- **移行要件の後回し** → 「移行要件」を独立セクション化
