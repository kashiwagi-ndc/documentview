# 確度表記の強制【最重要】
各記述には以下のタグを付与:
- [確定] SQL から明確に読み取れる
- [推測] テーブル名・カラム名・他のSQLから推測（理由併記）
- [要確認] 不明（マジックナンバーの意味 / 業務ルールの根拠が弱い等）

例:
- WHERE status = 1 → 「アクティブなレコードに絞り込み [推測：1=アクティブと推定、定数マスタ要確認]」
- LEFT JOIN ... ON deleted_flg = 0 → 「論理削除されていないものを結合 [推測：deleted_flg=0が有効レコード]」

# 注意事項
- 元のSQLにバグがある可能性も考慮（「正しい仕様」と決めつけない）
- 性能上の問題があれば指摘（ただしリバース解析が主目的なので、改善案は副次的）
- 不明なコード値・フラグ値は無理に意味を付けず[要確認]

# やってはいけないこと
- マジックナンバーの意味を推測のまま断定
- 「効率的に書かれている」等の主観的評価を確定として扱う
- バグの可能性を無視
- WHERE条件の業務ルール解釈で、データを見ずに断定

## 使い方のコツ
- **コードマスタや定数マスタの情報があれば必ず提供**する（マジックナンバーの解釈が劇的に改善）
- 「ビジネスロジックの抽出」セクションが最も価値が高い—設計書化の核になる
- 「不明点リスト」は次のステップ（元開発者への確認 / マスタ調査）に直結
- ストアドプロシージャの解析時は、呼び出し元・呼び出される側も含めて指定するのが理想

## 想定される失敗パターン
- **マジックナンバーの誤推測** → 「[要確認]」を必須化
- **元SQLのバグを「正しい仕様」扱い** → 「バグの可能性を考慮」を強化
- **業務ルールの過剰推測** → 確度タグの強制で予防
- **改善余地の混入** → 解析が主目的、改善は副次的とスタンス明示
