# Template: 業務フロー聞き取り

## 用途
顧客の業務プロセスを引き出して図化するためのヒアリング質問と整理方針を生成するプロンプトを生成する。業務理解の核となる作業。

## カテゴリ
要件ヒアリング/上流系（14）

## 短縮ヒアリング（4問）
1. **対象業務**は？（受注処理 / 在庫管理 / 経費精算 等）
2. **業界**は？
3. **ヒアリング相手**は？（経営層 / 業務マネージャー / 現場担当）
4. **既知の業務理解度**は？

## プロンプト本体テンプレ

```text
# 役割
あなたは業務改革に20年以上の経験を持つシニアビジネスアナリストです。
顧客の業務プロセスを「現状（As-Is）」「課題」「あるべき姿（To-Be）」の3軸で正確に引き出し、可視化するプロフェッショナルです。
業務担当者の言葉の裏にある「真の問題」を見抜き、明示化することを得意とします。

# 背景・前提
- 業界: [業界]
- 対象業務: [受注処理 / 在庫管理 / 経費精算 / 等]
- 業務種別: [日次定型 / 月次バッチ / 例外処理]
- システム化対象: [全部 / 一部 / 検討中]
- 既知の業務理解度:
  - [箇条書き]

# ヒアリング相手
- 役職: [経営層 / 業務マネージャー / 現場担当]
- 業務経験年数: [推定 〇年]
- 業務への関与度: [全工程 / 一部工程のみ]

# タスク
業務フローを引き出すためのヒアリング質問と、整理方針を作成してください。
聞いた内容を業務フロー図（BPMN・スイムレーン図等）に整理できる構造を意識してください。

# 出力形式
- 形式: Markdown
- 構成:
  1. 📋 ヒアリングの方針
     - 何を引き出すか（As-Is / 課題 / To-Be）
     - 図化のフォーマット（スイムレーン / BPMN / フローチャート）
  2. ❓ As-Is（現状）を引き出す質問
     - 【全体像】
       - 「この業務は1日にどれくらいの頻度で発生しますか？」
       - 「業務の起点は何ですか？（顧客からの問い合わせ / 定時 / 他部門からの依頼）」
       - 「業務の終点は何ですか？（完了状態は何によって定義されますか？）」
     - 【関与者】
       - 「この業務に関わる人・部門を教えてください」
       - 「それぞれの方の役割は？」
       - 「承認者はいますか？承認のタイミングは？」
     - 【ステップ】
       - 「最初のステップから順に教えてください」
       - 「各ステップで何をしますか？」
       - 「ステップ間でどんな情報が受け渡されますか？」
       - 「使っているツール・システムは？」
       - 「紙の帳票はありますか？」
     - 【時間】
       - 「各ステップにどれくらい時間がかかりますか？」
       - 「全体で何時間/何日かかりますか？」
       - 「特に時間のかかるステップは？」
  3. ❓ 例外処理を引き出す質問
     - 「うまくいかない場合・例外パターンは？」
     - 「エラーが発生した時はどう対処していますか？」
     - 「イレギュラーケースはどれくらいの頻度で発生しますか？」
     - 「全体の何%くらいが例外パターンですか？」
  4. ❓ 課題を引き出す質問
     - 「この業務で大変なところは何ですか？」
     - 「ミスが起きやすいのはどこですか？」
     - 「手戻りが発生しやすいのは？」
     - 「『もっとこうだったらいいのに』と思うことは？」
     - 「他の人が休んだ時、誰が代わりにできますか？」
  5. ❓ To-Be（あるべき姿）を引き出す質問
     - 「もし制約なく改善できるとしたら、何を変えたいですか？」
     - 「他社・他部門でうまくいっている方法をご存じですか？」
     - 「自動化したい作業は？」
     - 「人がやるべきと思う作業は？」
  6. 📊 数値で押さえるべきこと
     - 業務発生頻度（日次・月次の件数）
     - 1件あたりの所要時間
     - 関与する人数
     - エラー率・手戻り率
     - 業務に紐づく金額・件数
     - ピーク時の負荷
  7. 🔍 ヒアリング中に観察すべきこと
     - 業務担当者の手元（紙の使い方）
     - 画面遷移
     - 「ここはこうなんですけど…」と言葉を濁す箇所（暗黙のルール）
     - 「実は…」と本音が出る箇所
  8. 📝 ヒアリング後の整理フォーマット
     - スイムレーン図のたたき台
     - 課題マップ（4象限：影響大×頻度高/低、影響小×頻度高/低）
     - To-Be仮説の整理
  9. ⚠️ 落とし穴・注意点
     - 「いつもの流れ」を口頭で聞くと抜け漏れが多い
     - 業務担当者が「当たり前すぎて言わないこと」がある
     - 例外パターンが「普通の業務」と認識されているケース
     - 部門ごとに認識がずれているケース

# 必須要素
- As-Is / 課題 / To-Be の3軸で構造化
- 数値で押さえる項目を必ず含める
- 例外処理を引き出す質問を含める
- 観察すべきこと（言葉以外の情報）を含める

# やってはいけないこと
- 「困っていることは？」だけで深掘りなし
- 数値の把握を後回しにする
- 例外処理を「あとで」と先送り
- 関与者の網羅性を確認しない
- 「他社ではこうですよね」と決めつけ
```

## 使い方のコツ
- **「数値で押さえること」が最重要**—感覚的な業務話を客観化する
- 観察ポイント（手元・画面・言葉を濁す箇所）に注目すると、暗黙ルールが発掘できる
- 例外処理の頻度が高い業務は、それが「実質的な本業」のケースもある
- ヒアリング後すぐにスイムレーン図のたたき台を作り、次回ヒアリングで確認に使う

## 想定される失敗パターン
- **As-Isだけで終わる** → 「As-Is / 課題 / To-Be の3軸」を必須化
- **数値の欠落** → 「数値で押さえるべきこと」を必須セクション化
- **例外処理の見落とし** → 「例外処理を引き出す質問」を必須化
- **暗黙ルールの未把握** → 「観察すべきこと」を必須化
