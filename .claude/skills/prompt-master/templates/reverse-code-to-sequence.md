# Template: コード→シーケンス図

## 用途
複数クラス・複数モジュール間の呼び出し関係をシーケンス図として可視化するプロンプトを生成する。マイクロサービス間連携・複雑なオブジェクト連携の解析に使う。

## カテゴリ
リバースエンジニアリング系（12）

## 短縮ヒアリング（3問）
1. **対象**は？（特定のユースケース / 特定のクラス間連携 / API呼び出しフロー）
2. **入力コード**は？（@ファイルパス指定 / コピペ / 複数ファイル）
3. **どこから始める処理**ですか？（エントリポイント — 関数名・APIパス等）

## プロンプト本体テンプレ

```text
# 役割
あなたはオブジェクト指向設計・マイクロサービス設計に精通したシニアアーキテクトです。
複雑なクラス間・サービス間連携を、論理的に整理してシーケンス図として可視化するプロフェッショナルです。

# 背景・前提
- 対象システム: [システム名]
- 言語/プラットフォーム: [Java + Spring / TypeScript + NestJS / Go 等]
- アーキテクチャ: [モノリス / マイクロサービス / レイヤード]
- 解析対象: [特定ユースケース / 特定機能]
- 既存資料: [部分的にあり / 全くなし]

# 入力アクセス
[Claude Code向け]
以下のファイルを Read で読み込んで解析してください:
- @[ファイル1]
- @[ファイル2]
- @[ファイル3]

[他AI向け]
以下のコード一式を解析してください:
[コード貼り付け]

# 解析対象シナリオ
- エントリポイント: [関数名 / APIパス / イベント]
- ユースケース: [例：「ユーザーが注文を作成するフロー」]
- 終了条件: [例：「DB保存完了 + 通知送信完了」]

# タスク
上記シナリオにおけるクラス間・モジュール間の呼び出し関係をシーケンス図として復元してください。

# 出力形式
- 形式: Mermaid シーケンス図 + 解説テキスト
- 構成:
  1. 📋 概要
     - シナリオの目的（1〜2文）
     - 登場するクラス/サービス一覧
  2. 🔄 シーケンス図（Mermaid）
     ```mermaid
     sequenceDiagram
       participant A as ClientApp
       participant B as APIGateway
       participant C as OrderService
       participant D as PaymentService
       participant E as Database
       
       A->>B: POST /orders
       B->>C: createOrder(req)
       C->>D: charge(amount)
       D-->>C: payment_id
       C->>E: save(order)
       E-->>C: order_id
       C-->>B: 201 Created
       B-->>A: response
     ```
  3. 🔍 各ステップの詳細
     - ステップ番号・呼び出し元・呼び出し先
     - 渡される引数
     - 戻り値
     - 想定される例外
     - 確度タグ
  4. 🔀 分岐パターン
     - 正常系
     - 異常系（タイムアウト・エラーレスポンス等）
     - 非同期処理がある場合の扱い
  5. 💾 副作用
     - DB更新
     - 外部API呼び出し
     - メッセージ送信
     - キャッシュ更新
  6. ❓ 不明点（要確認リスト）
     - トランザクション境界が不明な箇所
     - 並行処理の有無が不明な箇所
     - エラーハンドリングが見えない箇所

# 確度表記の強制【最重要】
シーケンス図の各呼び出しと解説テキストに、確度タグを付与:
- [確定] コードから明確に追跡できる
- [推測] 呼び出しは確認できるが意図が不明（理由併記）
- [要確認] 動的呼び出し・リフレクション等で確定できない

# 注意事項
- 動的なメソッド呼び出し（リフレクション・DI コンテナ経由等）は静的解析では追跡困難
  → 「[要確認] DI設定要確認」と明記
- 非同期処理（Promise / Future / Goroutine）は別レーンで表現
- 例外処理を含むエラーフローも可能な範囲で記述

# やってはいけないこと
- 動的呼び出しを「確定」として扱う
- エラーフローを省略する（正常系だけにしない）
- 副作用を見落とす
- トランザクション境界を推測で書く
```

## 使い方のコツ
- **複数ファイルの場合は @path1 @path2 のように複数指定** — Claude Code で並列に読める
- **エントリポイント**を明示することで、AIがどこから追跡するかブレない
- マイクロサービスの場合はAPI Gateway層から書き起こすと全体像が見える
- 非同期処理が多いシステムは、シーケンス図に「Note over」で補足を入れさせるとよい

## 想定される失敗パターン
- **動的呼び出しの誤検出** → 「動的呼び出しは[要確認]」を必須化
- **異常系の省略** → 「分岐パターン（正常系・異常系）」を必須セクション化
- **副作用の見落とし** → 「副作用」を独立セクションとして必須化
- **トランザクション境界の誤推定** → 「トランザクション境界は[要確認]」を強調
