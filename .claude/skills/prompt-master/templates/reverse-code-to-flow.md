# Template: コード→処理フロー復元

## 用途
既存コード（関数・メソッド・モジュール）の処理を日本語の処理フローとして可視化するプロンプトを生成する。レガシーコード理解・引き継ぎ・設計書化の入口に使う。

## カテゴリ
リバースエンジニアリング系（12）

## 短縮ヒアリング（3問）
1. **対象コード**は？（@ファイルパス指定 / コピペ）
2. **対象範囲**は？（特定の関数のみ / クラス全体 / モジュール全体）
3. **出力形式**は？（テキストフロー / フローチャート（Mermaid） / 疑似コード）

## プロンプト本体テンプレ

```text
# 役割
あなたはレガシーシステム解析に精通したシニアエンジニアです。
コードから業務ロジックを正確に抽出し、推測と確定を明確に区別して報告するプロフェッショナルです。
分からないことを「分かる」と書くことは絶対にしません。

# 背景・前提
- 対象システム: [システム名・用途]
- 言語/プラットフォーム: [言語とバージョン / FW]
- コードベース規模: [単一ファイル / モジュール / プロジェクト全体]
- 既存資料の有無: [部分的にあり / 全くなし / コメントは英語]
- 解析の目的: [引き継ぎ / 設計書化 / 改修前の理解 / 移行検討]

# 入力アクセス
[Claude Code向け] 
@[対象ファイルパス] を Read で読み込んでください

[他AI向け]
以下のコードを解析してください:
[コード貼り付け]

# 対象範囲
- [特定の関数/メソッド: 〇〇()]
- [クラス全体: 〇〇クラス]
- [モジュール全体: 〇〇モジュール]

# タスク
対象コードの処理を、業務ロジックレベルで日本語の処理フローとして復元してください。

# 出力形式
- 形式: [Markdown / Mermaid フローチャート / 疑似コード]
- 構成:
  1. 📋 概要
     - 何をする処理か（1〜2文）
     - 主な入力・出力
  2. 🔍 詳細処理フロー（番号付き）
     - Step 1: [処理内容] [確度タグ]
     - Step 2: [処理内容] [確度タグ]
     - ...
  3. 🧩 主な分岐・例外処理
     - 分岐条件と処理
     - 例外パターンと処理
  4. 📊 入力・出力の詳細
     - 入力パラメータ（型・意味・想定値）
     - 戻り値（型・意味・null/エラー時の挙動）
     - 副作用（DB更新・外部API呼び出し・ファイルI/O等）
  5. ⚠️ 注意点
     - 想定される業務ルール
     - エッジケース
     - 潜在的なバグ・改善余地
  6. ❓ 不明点（要確認リスト）
     - [現コードでは判断できない事項]
     - [元仕様書か元開発者への確認が必要な点]

# 確度表記の強制【最重要】
各処理項目には以下のタグを必ず付与すること:
- [確定] コードから明確に確認できる
- [推測] 合理的に推測される（理由を併記。例：「変数名から〇〇と推測」「コメントの記述から〇〇」）
- [要確認] 不明または矛盾あり（理由を併記。例：「マジックナンバー42の意味が不明」）

「分からないことを分かる」と書くことは厳禁。「不明」と書く方が価値があります。

# やってはいけないこと
- 推測を確定と区別せず書く
- コードに書かれていない業務ルールを断定的に書く
- 「たぶん」「おそらく」だけで断定的な表現を使う（必ず[推測]タグ）
- 元コードのバグを「正しい仕様」として記述する
```

## 使い方のコツ
- **Claude Code環境では `@ファイルパス` 指定が圧倒的に効率的**
- 「目的」を明示すると、出力の粒度がそれに合わせて調整される（引き継ぎなら詳細、改修前なら影響範囲中心）
- 出力にMermaidフローチャートを含めると、設計書への転用が早い
- 「不明点リスト」を必ず作らせることで、後で元開発者に確認すべき項目がクリアになる

## 想定される失敗パターン
- **推測の混入を見逃す** → 「確度表記の強制」を最重要として明示
- **業務ルールの過剰推測** → 「コードに書かれていない業務ルールは断定しない」を強化
- **マジックナンバーの意味補完** → 「不明な定数は[要確認]」を必須化
- **副作用の見落とし** → 「副作用（DB/API/ファイル）」セクションを必須化
