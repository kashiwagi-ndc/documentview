# Template: スロークエリ最適化

## 用途
遅いSQLの性能を改善するためのプロンプトを生成する。EXPLAIN実行計画を前提とした体系的なチューニング。

## カテゴリ
DB/SQL系（13）

## 短縮ヒアリング（4問）
1. **DBエンジン・バージョン**は？
2. **現在のSQLとEXPLAIN結果**はありますか？（@ファイルパス / 貼り付け）
3. **テーブル定義とインデックス情報**は？
4. **現在の実行時間と目標値**は？

# DBエンジン固有の最適化観点
[エンジンに応じて]
- PostgreSQL: VACUUM/ANALYZE状況、HOT更新、Bitmap Index Scan、Parallel Query
- MySQL: Covering Index、 EXPLAIN FORMAT=JSON、Join Buffer、Optimizer Trace
- Oracle: Hint、Bind変数、Histogram、Adaptive Plan、HashJoin/NestedLoopの選択
- SQL Server: Index Seek vs Scan、Statistics、Query Store
- BigQuery: Partition Pruning、Clustering、Slot使用量
- Snowflake: Pruning、Clustering Key、Warehouse Size

# 改善優先順位の付け方
1. インデックス追加・修正（実装コスト低・効果大）
2. SQL書き換え（実装コスト低・効果中〜大）
3. パーティション/クラスタリング戦略（実装コスト中・効果大）
4. スキーマ変更・非正規化（実装コスト高・効果大）
5. ハードウェア・設定パラメータ（最後の手段）

# 必須要素
- ボトルネックを実行計画の具体的なオペレーションで指摘
- 改善案には必ず「期待効果」「実装コスト」「副作用」
- 検証方法を必ず提示
- 既存クエリへの副作用を考慮

# やってはいけないこと
- 「インデックスを貼れば速くなる」等の一般論
- 実行計画を見ずに改善案を出す
- 副作用を考慮しない改善案
- 検証方法を提示しない
- 「全部のテーブルにインデックスを」等の乱暴な提案

## 使い方のコツ
- **EXPLAIN ANALYZE実行結果が最重要** — これがないと推測ベースの一般論になる
- 「実行頻度」を伝えることで、改善コストに見合うかが判断できる
- 並行実行が多いクエリは、ロック・MVCC観点も含めた検討が必要
- インデックス追加提案は、更新性能への影響評価とセットで

## 想定される失敗パターン
- **EXPLAIN なしで一般論** → 「EXPLAIN実行計画を必須化」
- **インデックス乱用** → 「更新性能への影響を必ず評価」
- **副作用の見落とし** → 「他クエリへの影響を必須化」
- **検証手順なし** → 「検証手順」を必須セクション化
