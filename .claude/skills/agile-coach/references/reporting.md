# 自動報告のセットアップ（日次・週次・月次）

> 進行役（agile-coach）が、立ち上げ時のヒアリングで「自動報告が必要」と分かったときに読む手順書。
> **要否 → タイミング → 報告先 → 送信方法（アダプタ）→ 初回ドライラン → 自動化**の順で進める。
> キットは他環境でも動く前提なので、**送信の仕組みは環境に合わせて選ぶ「アダプタ方式」**。特定のツールに依存させない。
>
> **★自動化の原則（オプトイン＋終了条件）**：自動報告は**利用者/顧客が明示的に依頼したときだけ**設定する（既定OFF）。設定と同時に**"止め方・終了条件"（プロジェクト完了時／期限日／N回で見直し）も決めて `自動報告設定.md` に記録**する。**プロジェクトが終わったら必ず停止**し撤収する（`docs/templates/プロジェクト終了チェックリスト.md`）。走りっぱなしの自動化を残さない（通知垂れ流し・鍵残存・古いデータでの誤動作を防ぐ）。⑧ふりかえりで「まだ必要か」を定期点検。

## ステップ1：要否とタイミングを確定する（選択式）
`AskUserQuestion` で聞く。

1. **自動報告は必要？**：必要／不要（不要ならここで終了・作らない）。
2. **頻度はどれ？（複数可）**：
   - **日次**：例「平日 毎朝9:00」。中身＝前日の進捗・今日の予定・ブロッカー・ボード状態（デイリーの要点）。
   - **週次**：例「毎週金 17:00」。中身＝今週の成果・ベロシティ・KPI現在値・来週の予定（`docs/templates/報告書（週次・成果）.md`）。
   - **月次**：例「月末 最終営業日」。中身＝成果サマリ・KPI/OKRの差分・コスト/工数・次月方針（`報告書（週次・成果）.md` の成果版＋`KPI・OKRトラッキング.md`）。
3. **正確な日時**：曜日・時刻・タイムゾーンを確定（cron式に落とす。例 週次=「0 17 * * 5」JST）。

## ステップ2：報告先を確定する（選択式）
- **どこへ送る？（複数可）**：Teams ／ Slack ／ メール ／ PMツール（Wiki/チケットにコメント）／ その他。
- チャネル/宛先の具体（チャネル名・メーリングリスト・WikiページID）を控える。**URL・トークン等のシークレットは値を画面に出さない**（環境変数/secretsの名前だけ記録）。

## ステップ3：内容（レポート本文）を組み立てる ― 社内向け・やさしい日本語・表/図解中心
**様式は `docs/templates/自動報告_レポート様式.md` に従う。** 既定の主な読み手＝**開発チーム（社内）**＝価値訴求より**動き・詰まり・遅れの予兆・重複/衝突**を主役にする。原則：
- **表・図解が主、文章は補足（1〜3行）**。図解は文字バー（`████░░ 60%`）で十分。
- **やさしい日本語を主に使い、アジャイル語は括弧で初出だけ**（例：反復（スプリント）／今回の目標（スプリントゴール）／残り作業の減り具合（バーンダウン）／進む速さ（ベロシティ）／詰まり（ブロッカー））。対応表は様式テンプレ参照。
- **赤は赤で先出し**（遅れ・滞留を先頭、無い項目は「なし」と明示）。**数値はツールから取り、AIに進捗を創作させない**（未確定は「未確定」）。**個人の監視にしない**（人別は調整用、評価に使わない）。
- 中身：**日次＝朝会の事前資料**（キットの朝会4点に対応：今日やる(#)／今日触る所／詰まり＋重複衝突の兆候＋残り作業の位置）。**週次＝反復の健康診断**（減り具合・このままいくと終わる見込み・滞留・持ち越し→次の一手）。**月次＝傾向と健康度**（進む速さ等の推移・改善の効き・負債）。素材は `agile-state.md`・スプリントボード・`報告書（週次・成果）.md`・`メトリクス計測シート.md`・`KPI・OKRトラッキング.md` から流用（二重メンテしない）。
- **セレモニー連動（イベント駆動・cronでない）**：成果デモ会（スプリントレビュー）後＝完了一覧、ふりかえり（レトロスペクティブ）後＝点検＋改善1〜3（社内向け・個人評価に使わない）。
- **関係者（経営・顧客）向けは派生**：社内版から価値・KPIダイジェストに絞って別送信（人別は出さずチーム集計）。
- **レンダリング二段構え**：フル版＝HTML（メール/Wiki に表＋バー）、チャット版＝ダイジェスト（Teams/Slack に要点表＋文字バー＋フル版リンク）。
- 生成は**並列サブエージェント**で下書き→**人が確認**。**本番データ・個人情報は載せず要約**にする。

## ステップ4：送信アダプタを選ぶ（環境に合わせる）
報告先 × 送信手段を、その環境で使えるものに合わせて選ぶ。**どれも「送信先のシークレットは環境変数/secrets管理」「値はコミット・ログ・画面に出さない」**が前提。

| 報告先 | 送信手段（例） | 要点 |
|---|---|---|
| **Teams** | Incoming Webhook（チャネルのWebhook URLへ JSON を POST） | URLはシークレット。MessageCard/Adaptive Card形式。チャネル名を必ず確認 |
| **Slack** | Incoming Webhook ／ Slack MCP（あれば） | Webhook URLはシークレット。投稿先チャネルを確認 |
| **メール** | メールMCP（Gmail等）で下書き→送信 ／ SMTP | 宛先を必ず確認。初回は下書き(Draft)で人が確認 |
| **PMツール** | API でWikiページ追記／チケットにコメント（Redmine/Jira等） | 既存の連携（`tool-integration.md`）を再利用。書き込みは事前確認 |

> アダプタは「本文（md/テキスト）→ 各先の形式に整形して送る」だけの薄い層。報告内容の作り方（ステップ3）は送信先に依存させない。

## ステップ5：スケジューラ（起動役）を選ぶ ― チームは「1ランナーに集約」
> **チーム運用の鉄則：自動送信は"1つの共有ランナー"だけで動かす**。各メンバーのPCでcronを回すと**人数分の多重送信**になり、シークレットも各端末に散る。**読み取り元（PMツール）と起動役（スケジューラ）と送信先は別レイヤー**＝起動役がGitHub Actionsでも、PM管理がRedmine等のGitHub以外でも問題ない（APIで読むだけ）。

| スケジューラ | 向き | 要点 |
|---|---|---|
| **CI（GitHub Actions の schedule）** ★チーム第一候補 | リポジトリ運用ができる | `on: schedule:` で人数に関係なく1回だけ実行。secretsにWebhook/APIキーを集約。**PM管理がRedmine等でもAPIで読める**（サンプル：`docs/examples/自動報告_GitHubActions_redmine.yml.sample`＋`自動報告_redmine_to_chat.py.sample`） |
| **常時起動の1台でOS cron／Windowsタスクスケジューラ** | CIが無い／常時ONのサーバ・代表PCがある | その1台だけで起動（多重送信を避ける）。スクリプトは上のpythonサンプルを流用 |
| **クラウドスケジューラ / VPSのcron** | 常時ONのPCを置きたくない | PC電源に依存しない |
| **Claude Code スケジュールタスク** | その1台でClaude Codeを定期実行できる | 生成も送信もClaude Codeで完結。`create_scheduled_task`等 |

> GitHub Actions の cron は **UTC**（JSTは-9時間で書く）。Linuxランナーなので Windowsローカルの `--ssl-no-revoke` 等は不要。
> **再ヒアリング防止**：進行役は立上げ時に既存の `docs/templates/自動報告設定.md` があれば**要否ヒアリングを飛ばして設定に従う**（メンバーごとに聞き直さない）。設定に「**送信役（ランナー）＝どのCI/どの1台**」を明記し、そこだけで動かす。

## ステップ6：初回はドライラン → 承認 → 自動化（重要）
- **いきなり自動送信しない**。初回は**ドライラン**（または下書き）で本文・宛先・整形を人が確認する。
- 確認OKになってから、ステップ5のスケジューラに登録して定期自動化する。
- 設定一式は `docs/templates/自動報告設定.md` に記録（要否・頻度・cron・報告先・送信手段・内容ソース・承認方針・停止方法）。

## 読み取り元アダプタ（どのPMツールでも＝ツール非依存）
本方式は**PMツールに依存しない**。読み取り元（②）が次を満たせば、Redmineでも Jira でも Backlog でも GitHub Issues でも同じ仕組みで動く＝**薄い「読み取りアダプタ」を差し替えるだけ**。
- 課題/タスクを **状態・担当・見積り・日付・スプリント（版）** で取得できるAPI
- （定例駆動なら）**開催日に当たる日付**と**種別**を持つ"会議アイテム"が作れ、そこに**コメント/メモを書き戻せる**

| 概念（キット） | Redmine | Jira | Backlog | GitHub Issues |
|---|---|---|---|---|
| 課題/タスク取得 | `GET /issues.json` | REST `/search`（JQL） | 課題一覧API | Issues API / GraphQL |
| 認証 | `X-Redmine-API-Key` | Basic/トークン | `apiKey` | トークン |
| 予定工数 | `estimated_hours` | `timetracking` | 予定時間 | （標準に無し→Projectsのフィールド/ラベルで代替） |
| スプリント/版 | `fixed_version` | Sprint/ボード | マイルストーン | Milestone |
| 定例の開催日 | `due_date` 等 | 期限/カスタム | 期限日 | Milestone期日 / Issue＋ラベル |
| 定例の種別 | カスタムフィールド | ラベル/課題タイプ | 種別/カテゴリ | ラベル |
| レポートを書き戻す | チケットにメモ(notes) | コメント追加 | コメント追加 | Issueコメント |

> 同梱サンプルは **Redmineを worked example** にしているだけ。別ツールなら、この表に沿って読み取り/書き戻しの数行を差し替える（様式・スケジューラ・送信先はそのまま）。

## 定例レポート（推奨：PMツールの「定例チケット」を日程の正本にする）
各種定例（朝会・週次定例・月次報告会・成果デモ会・ふりかえり）に合わせてレポートを出す。**PMツールの定例チケット/課題を"開催日程の正本＋レポートの置き場＋議事録の土台"**にする（Redmineに限らず Jira/Backlog/GitHub Issues でも同様）。
> 前提：多くのSaaS PMツールは**外部へpushしない／できない**（Webhook/プラグイン不可が普通）＝ツールが自分からActionsを起動はしない。だから**Actionsは定期tickし、ツールを"見にいく"**（ポーリング）。以下はRedmineを例に説明するが、上の対応表で他ツールに読み替えられる。

**しくみ**
```
GitHub Actions（毎営業日の朝などにtick）
  → Redmineで「今日が開催日の"定例チケット"」を検索（トラッカー=定例 等・due_date=today）
  → 各定例の"種別"に合うレポート様式を生成
  → ① その定例チケットに【コメント追記】（会議の記録に残す）
  → ② チャット（Teams/Slack）にも要点＋チケットURL
```

**定例チケットの作り方（②立上げ or 運用開始時に登録）**
- **トラッカー/種別**＝「定例」。**種別フィールドで様式を出し分け**：
  | 定例 | 種別 | 出す様式（`自動報告_レポート様式.md`） |
  |---|---|---|
  | 朝会（毎日） | 朝会 | 日次（動き・詰まり・重複/衝突） |
  | 週次定例 | 週次 | 週次（反復の健康診断） |
  | 月次報告会 | 月次 | 月次（傾向と健康度） |
  | 成果デモ会（スプリントレビュー） | レビュー | セレモニー（完了一覧） |
  | ふりかえり（レトロスペクティブ） | レトロ | セレモニー（点検＋改善） |
- 項目：**開催日（`due_date` 等）／種別／参加者／アジェンダ**。繰り返し定例は、開催のたびにチケットを起票（または期日を更新）。
- レポートは**その回の定例チケットにコメント**＝アジェンダ→事前レポート→当日議事録→決定/ToDo が1か所に並ぶ。
- 日程変更は**チケットの開催日を直すだけ**（cronを書き換えない＝1情報1正本）。

**サンプル**：`docs/examples/自動報告_GitHubActions_redmine.yml.sample`（毎営業日tick）＋`自動報告_redmine_to_chat.py.sample`（定例チェック→種別判定→チケットへコメント＋チャット送信）。

## KPIダッシュボードをPMツールのWikiに表示（日々更新）
プロジェクトのKPIを**PMツールのWiki（Redmine Wiki等）に1ページ作り、ランナーが毎日上書き**して“今の状況”を見せる。
```
毎営業日tick → KPI原本（repoのmd）＋Redmine自動算出 → 「KPIダッシュボード」Wikiページを上書き(PUT)
```
- **原本はrepoのmd、Wikiは派生ビュー**（下の「原本」ルールと同じ）。Redmine Wiki更新は `PUT /projects/{id}/wiki/KPIダッシュボード.json` `{"wiki_page":{"text":"..."}}`。表＋文字バーで表示（画像不要）。
- **KPIは2種類（出どころが違う）**：
  | 種類 | 例 | 現在値の出どころ |
  |---|---|---|
  | **自動算出**（PMツールから） | 進む速さ（ベロシティ）・完了件数・進捗率・リードタイム・工数の予実 | ランナーがAPIで毎日計算 |
  | **業務KPI**（人が測る） | 「見積り時間 30→5分」等、①で定めた価値 | `docs/templates/KPI・OKRトラッキング.md` を人が更新（⑧等）。**未更新なら「未更新」と表示**（数値を創作しない） |
- 中身：KPI/OKR表（目標→現在→差分＋バー）＋今日の状況（ボード・進む速さ・リードタイム）＋更新時刻＋原本(md)へのリンク。
- **ツール非依存**：Confluence/Notion/Backlog Wiki も同じ（ページ上書きAPI）。「読み取り元アダプタ」の表で読み替える。
- 1ランナーで更新（各PCで上書き合戦をしない）。書き込みは事前確認、認証はsecrets。

## レポートの原本は repo の md（docs-as-code・1情報1正本）
キット全体の原則どおり、**自動報告も「原本＝リポジトリのmd」**にする。チャット/チケットは派生ビュー。
```
原本：docs/報告/ に md で保存（履歴・差分・監査が効く・チャット履歴が流れても残る）
  └→ チャット（Teams/Slack）：要点ダイジェスト＋原本リンク
  └→ 定例チケット（Redmine等）：コメントに本文 or 原本リンク（会議の記録）
  └→ メール/Wiki：必要なら原本から整形して送る
```
- **保存先・命名**：`docs/報告/報告_<種別>_<日付>.md`（例 `報告_週次_2026-06-19.md`）。キットの**ユニーク命名（種別＋識別子）**に従う。
- **誰が書くか**：CI（GitHub Actions）ならジョブ内で md を生成→**repo に commit**（1ランナーなので二重保存にならない）。常時ON1台のcronなら作業コピーに書き出し（必要なら commit/push）。
- **二重メンテにしない**：原本は md の1つだけ。チャット・チケット・メールは原本から作る“見せ方違い”で、内容は持ち回らない。
- 図解の文字バーは md でもそのまま読める。HTML が要る送信先（メール/Wiki）だけ md→HTML に整形する。

## 安全ルール（機密3原則・誤送信防止）
- **シークレット管理**：Webhook URL・APIトークン・メール認証は**環境変数/secrets**から読む。コード・ログ・コミット・チャットに値を出さない。
- **送信先の確認**：自動化の前に、チャネル名・メール宛先を必ず人が確認（誤チャネル・誤送信の防止）。外部送信は目的と送信先を伝えてから。
- **載せない**：本番データ・個人情報・機密はレポートに載せない（数値は集計・要約で）。対外向けは人の最終確認を必須にする。
- **止められること**：いつでも停止/一時停止できる手順を設定に残す。失敗時は再送せず通知だけにするなど、暴走させない。
