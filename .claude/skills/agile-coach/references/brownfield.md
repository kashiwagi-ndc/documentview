# 既存プロジェクトをアジャイルのレールに乗せる（ブラウンフィールド）

既に動いているプロジェクトに後からアジャイルを入れる場合の手順。
**いきなりやり方を変えない。まず現状を把握し、最小限のギャップから埋める。**

---

## ステップ1: 現状を調べる（読むだけ・変えない）

次を確認し、分かったことを `docs/agile-state.md` にメモする。
（コードや設定は**読み取りのみ**。この段階で変更・削除はしない。）

| 調べる対象 | 見るもの | 分かること |
|---|---|---|
| ドキュメント | README / docs / wiki | 目的・構成・運用ルール |
| リポジトリ | git log・ブランチ運用・コミット頻度 | 開発のリズム・関与メンバー |
| 課題管理 | 既存のIssue/チケット/バックログ | やることの溜まり方・優先順位の付け方 |
| 品質 | テストの有無・CI・カバレッジ | 品質の作り込み度合い |
| リリース | リリース頻度・手順・切り戻し | デリバリーの安定度 |
| チーム | 今の進め方・会議体（朝会・ふりかえり有無） | アジャイル成熟度 |
| 技術スタック | package.json/requirements.txt/go.mod 等 | ④⑤⑥の前提（CLAUDE.mdへ記録） |

> CLAUDE.md がなければ、ここで把握した build/test コマンド・規約・技術スタックを下書きする提案をする。

### ステップ1.5: 既存ドキュメントの「型（フォーマット＋粒度）」を抽出して踏襲する

既存・顧客提供のドキュメント様式がある場合は、**独自テンプレを押し付けず、その型に合わせて作る**（顧客優先）。

1. **代表サンプルを1つ読む**：既存の仕様書・設計書・報告書など、これから作る種類に近いものを1つ選んで読み込む（Word/Excel/PDF/md いずれも）。
2. **型を抽出する**：
   - **形式**：md／HTML／**Excel(.xlsx)**／**Word(.docx)**／PDF（提出物がExcel/Wordなら `xlsx`／`docx`／`pdf` スキルで生成）。
   - **章立て・項目**：見出し構成・必須項目・表の列・記載順。
   - **粒度**：どこまで細かく書くか（1機能1ページ／要点のみ 等）。既存に合わせて最小／標準／詳細を決める。
   - **命名・言語**：ファイル名の付け方・日本語/英語。
3. **記録する**：抽出した型と参照元（サンプルのパス・様式名）を `docs/agile-state.md` の「ドキュメント方針／既存フォーマット参照」に書く。以降の全工程はこの型で作る。
4. **判断**：既存様式が無い・薄い場合のみ、本キット標準テンプレ（`docs/templates/`・日本語の工程別フォルダ）を既定として使う。

> 原則：**既存があれば踏襲、無ければ標準**。顧客提出物（Excel/Word指定など）は顧客の様式が最優先（just enough より顧客要件が上）。

## ステップ2: 8工程にマッピング（できている／欠けている）

現状を工程①〜⑧で整理する。例：

| 工程 | よくある既存の状態 | 欠けがちなもの |
|---|---|---|
| ① 構想・適合性 | 目的はあるがKPIが曖昧 | **価値・KPIの明文化** |
| ② 立上げ | チームはいるが役割が暗黙 | 役割の明確化・メンバー一覧 |
| ③ 計画 | 課題は並ぶが仕様が曖昧 | **仕様メモ**・不確実性の洗い出し |
| ④ 実装 | 動いている | AI活用の安全ルール |
| ⑤ テスト | テストが薄い場合あり | TDD・脆弱性検査（/tdd-ai） |
| ⑥ レビュー | レビューはあるが観点バラバラ | 5観点・検証ゲート |
| ⑦ リリース | リリースはしている | 切り戻し・脆弱性対応プロセス |
| ⑧ ふりかえり | やっていない場合が多い | **定期ふりかえり・価値測定** |

## ステップ3: ギャップを埋めてレールに乗せる（最小限から）

**一度に全部変えない。** 効果が高く負担が軽い順に、次の1スプリントから入れる。
**新しいファイル（CLAUDE.md・各メモ等）を作る前に、必ず内容を提案してユーザーの承認を得てから作成する**（既存ファイルの上書きは特に慎重に）。

優先度の目安（多くの既存プロジェクトで効く順）：
1. **CLAUDE.md を整える**（AIが迷わない土台）
2. **価値・KPIを遡及定義**（①の構想メモテンプレを使う）
3. **既存の課題をバックログとして整理**（②）。ツールがあれば既存Issueをそのまま使う（フェーズ1.6）。
4. **次スプリントを③で計画**（仕様メモ＋スプリントボード）。ここから通常フロー合流。
5. **ふりかえり（⑧）を定例化**（多くの既存チームに一番効く）

> 既存の良い習慣（独自のレビュー文化・運用手順など）は**置き換えず接続**する。テーラリング＝ちょうど十分に。

## ステップ4: 合流

ギャップ補完が一巡したら、**③スプリント計画**から通常のサイクル（③→④→⑤→⑥→⑧）に合流する。
`docs/agile-state.md` に「既存プロジェクトを移行中／現在③」と記録して続ける。

---

## 注意
- 読み取りで分かった事実だけを根拠にする。推測は「たぶん」で断定しない。
- 既存メンバーの今のやり方を否定しない。**段階的に・合意の上で**入れる。
- 破壊的な変更（大規模リファクタ・運用変更）は、この移行とは切り離し、別途バックログに積む。
